## 1. 핵심 요약

Persnapse는 명함과 만남 맥락을 저장하고, 이름을 잊어도 맥락으로 사람을 다시 찾아 행동하도록 돕는 관계 기억 제품이다. OCR은 입력 수단이며, 핵심 가치는 **정확한 사람을 관계 이유와 함께 다시 찾는 경험**에 있다.

현재 데이터 저장, 사용자 확인, 실제 명함 OCR, 기본 검색, 비용 방어와 보호된 Preview 배포가 구축돼 있다. 그러나 사용자 관점에서 핵심 경험의 유용성과 편의성이 충분히 검증된 상태는 아니다.

| 구분         | 핵심 내용                                                                          |
| ------------ | ---------------------------------------------------------------------------------- |
| 현재 단계    | 승인된 팀원이 공유 데이터를 사용하는 내부 테스트용 프로토타입                      |
| 확보한 기반  | 관계 데이터, 출처 보존, 검토 후 저장, 중복 저장 방지, 실제 OCR, 보호 배포          |
| 가장 큰 차이 | 실제 OCR과 달리 Preview 맥락 구조화는 mock이며, Recall은 로컬 검색 기반            |
| 제품 측 공백 | 자유로운 입력·질문의 품질, 간결한 모바일 흐름, 반복 사용 가치 검증                 |
| 권고 방향    | 기존 기반 위에서 명함·맥락 저장 → 이름 없는 회상 → 근거 확인 → 연락의 한 흐름 완성 |
| 후순위 후보  | 음성, 그래프, 다중 명함 자동 분리, AI 이미지 복원, 다중 Agent 확장                 |

### 읽는 기준

- **확인 사실:** 코드에서 확인한 구현 또는 기존 검증 기록.
- **분석·판단:** 확인 사실에 근거한 해석. 사용자 테스트로 확정한 결론과 다름.
- **위험·가설:** 실패 가능성이 있어 별도 검증이 필요한 항목.
- **제안:** 다음 개선 방향. 기존 승인을 변경하거나 새로운 구현을 승인하는 문구가 아님.

## 2. 제품 의도와 핵심 질문

### 제품 정의와 사용자

명함과 만남의 맥락을 신뢰 가능한 관계 기억으로 저장하고, 필요한 순간 정확한 사람과 근거를 회상해 다음 행동을 판단하도록 돕는다.

- 초기 대상: 외부 만남과 후속 연락이 잦은 Sales / Business Development 사용자.
- 최초 상황: 행사·미팅에서 명함과 짧은 메모를 남기고, 며칠 또는 몇 주 후 장소·주제·약속으로 사람을 다시 찾음.
- 핵심 질문: “연락처만 저장했을 때보다 이 사람을 더 잘 기억하고, 필요한 순간 활용할 수 있는가?”

```text
명함·메모 입력 → 맥락 확인 → 관계 기억 저장 → 이름 없이 다시 찾기 → 근거 확인·연락
```

### 유지할 원칙

- 이름이 같다는 이유로 사람을 자동 병합하지 않는다.
- 사용자의 확인·수정이 AI의 추정보다 우선한다.
- 검토 전 임시 정보와 확정된 기억을 구분한다.
- 검색 결과는 실제 기록과 출처에 근거한다.
- 저장된 약속과 새로 제안한 행동을 구분한다.
- OCR·그래프·음성 등 개별 수단이 핵심 경험 검증을 지연시키지 않게 한다.

## 6. 사용자 피드백과 분석·판단

### 6.1 기반 구축이 복잡해 핵심 경험이 지연됨

**사용자 피드백:** 핵심 기능을 먼저 경험해야 하는데 기반 구축이 복잡해져 MVP 개발이 지연됐다.

**판단:** 개발 순서가 제품 학습보다 기술적 준비에 치우쳤다. 폭넓은 데이터 구조·모델 라우팅·독립 API 검증·운영 절차에 비해 핵심 화면과 사용자 테스트의 우선순위가 낮았다. 다만 기록만으로 작업별 지연 시간과 기여도를 정량화할 수는 없다.

**제안:** 기반 확장을 잠시 멈추고 한 가지 사용 흐름을 완성한다. 인물 오연결 방지, 사용자 수정·출처 보존, 중복 저장·과금 방어, 비밀정보 보호는 유지한다. 기반 폐기나 전면 재설계를 선행하지 않는다.

### 6.2 의도대로 구현됐는지 확인하기 어려움

**사용자 피드백:** 초기 설계 의도와 핵심 기능의 구현 상태를 판단하기 어렵다.

**판단:** 완료 보고가 구현·테스트 통과에 집중돼 제품 연결과 사용자 성공을 충분히 구분하지 못했다. mock·live·고정 문구의 혼재도 능력 판단을 어렵게 한다.

**제안:** 완료 기준을 “입력 내용이 맞게 저장됐는가 → 다른 표현으로 다시 찾는가 → 근거를 보고 행동할 수 있는가”로 바꾼다. 예시 기반 성공과 새로운 실제 입력 성공을 분리한다.

### 6.3 UI/UX 완성도가 낮음

**사용자 피드백:** UI/UX가 조악하다.

**판단:** 시각적 다듬기뿐 아니라 화면의 목적, 정보 순서와 언어를 정리해야 한다. 다음은 코드 검토에 근거한 문제와 제안이다.

| 관찰                                    | 영향 또는 검증할 위험              | 개선 제안                                    |
| --------------------------------------- | ---------------------------------- | -------------------------------------------- |
| 홈의 큰 소개 문구·Core Loop 설명        | 반복 사용의 작업 시작점이 약함     | 검색·명함 추가·최근 기록 우선                |
| Person·Draft·Memory·원자적 저장 등 용어 | 내부 구조를 이해해야 하는 부담     | 사람·저장 전·만남 기록·저장 중으로 변경      |
| 긴 구조화 검토 폼                       | 입력·확인 작업 반복                | 핵심 요약 먼저, 상세 수정은 필요할 때        |
| 결과마다 여러 근거·행동 패널            | 누구를 왜 찾았는지 파악하기 어려움 | 사람 → 일치 이유 → 대표 근거 → 행동 순서     |
| 고정 문구를 AI 제안으로 표시            | 실제 능력에 대한 오해              | 일반 안내로 변경하거나 실제 생성 시에만 표시 |
| 모바일 전용 탐색 구조 부족              | 좁은 화면 탐색·입력 불편 가능성    | 실기기에서 탐색·키보드·저장 버튼 검증        |
| 명함 이미지 위 정보 오버레이            | 원형 명함 일부를 가릴 가능성       | 이미지 확인과 연락처 요약 분리               |

상세 정보를 접어 두더라도 중요한 인물 연결과 오류 수정은 명시적으로 유지한다. 줄일 대상은 반복 설명과 부가 필드의 노출이다.

## 7. 우선 확인할 기능적 위험

### 검색 근거의 존재와 질문 적합성은 다름

- 확인 사실: 검색은 단어·유사도 점수와 행동·시간 유형별 가산점을 사용한다.
- 위험: 실제 기록을 보여줘도 질문의 모든 조건을 충족하지 않을 수 있다.
- 검증 예: “부산에서 만난 사람”과 “부산 사업을 이야기한 사람”을 구분하는가? 시간·장소·주제가 같은 만남에 연결되는가?
- 상태: 특정 실제 질의의 오답을 재현한 판정이 아니라, 코드 구조상 필요한 추가 검증이다.

### 메모 작성 시점과 만남 시점이 섞일 수 있음

- 확인 사실: mock은 명시적인 날짜가 없으면 기준 시각을 사용하며 “어제”를 실제 어제 날짜로 해석하지 않는다.
- 위험: 과거 만남을 오늘의 만남으로 저장할 수 있다.
- 제안: 실제 구조화와 상대 시간 평가를 연결하고, 모르는 날짜는 미확인 또는 사용자 확인 대상으로 처리한다.

### 모델 연결만으로 Recall 품질이 완성되지 않음

embedding·reranking은 저장 내용·검색 조건·근거 선택 오류를 자동으로 해결하지 않는다. 실제 실패 사례를 확보하고 해당 문제를 해결하는 최소 연결을 선택한다. 연결하는 모델마다 호출 제한·timeout·비용 경계를 확인한다.

## 8. 제안하는 다음 작업 범위

### 목표 경험

> 내 명함 한 장과 만남 메모를 저장하고, 이름 없이 다시 찾아 근거를 확인한 뒤 연락할 수 있다.

| 순서 | 작업                           | 완료 판단 기준                                                 |
| ---- | ------------------------------ | -------------------------------------------------------------- |
| 1    | 화면·용어·검토 흐름 정리       | 도움 없이 촬영·메모·저장까지 진행                              |
| 2    | 실제 맥락 구조화 연결          | 예시 밖 메모를 수정 가능한 결과로 변환                         |
| 3    | 실제 입력으로 Recall 평가·개선 | 표현 변화에도 적절한 사람·근거 제공, 없는 조건은 단정하지 않음 |
| 4    | 모바일 전체 흐름 확인          | iPhone·Android에서 저장 → 검색 → 연락까지 완주                 |
| 5    | 소수 사용자 관찰·반복 개선     | 막힌 지점과 재사용 의향을 근거로 다음 범위 결정                |

순서는 제안이다. 기존 Phase 번호보다 핵심 경험의 실패 지점에 따라 조정한다.

### 화면별 최소 역할

| 화면         | 주요 내용                                  |
| ------------ | ------------------------------------------ |
| 홈·검색      | 검색창, 명함 추가, 최근 기억               |
| 명함 추가    | 명함 이미지, 이름·회사, 짧은 만남 메모     |
| 저장 전 확인 | 인물 연결, 만남 요약, 약속, 저장           |
| 검색 결과    | 인물·회사, 일치 이유, 대표 근거, 상세 보기 |
| 사람 상세    | 명함, 최근 만남, 약속, 연락 버튼           |

### 유지·보류 기준

| 유지할 것                       | 당장 확장하지 않을 것              |
| ------------------------------- | ---------------------------------- |
| 사용자 확인과 인물 오연결 방지  | 음성·그래프                        |
| 실제 근거와 사용자 수정값 보존  | 다중 명함 자동 분리·AI 이미지 복원 |
| 임시 데이터 격리·중복 저장 방지 | 복잡한 행동 추천·자동 실행         |
| 비밀정보·접근·과금 방어         | 다중 Agent·범용 모델 구조 확장     |

보류는 영구 제외가 아니다. 텍스트 입력 때문에 기록을 포기하는 문제가 반복 관찰되면 음성의 우선순위를 다시 평가한다.

## 9. 검증·완료 보고 방식 제안

### 핵심 경험 평가

개발 예시에 없는 명함·메모로 다음을 확인한다.

1. 도움 없이 등록하고 맥락을 남기는가?
2. 이름 없이 장소·주제·약속으로 원하는 사람을 찾는가?
3. 다른 표현으로 질문해도 적절한 결과가 나오는가?
4. 없는 조건에는 관련 없는 사람을 단정하지 않는가?
5. 근거를 읽고 맞는 사람인지 판단할 수 있는가?
6. 연락처를 이용해 다음 행동을 시작할 수 있는가?

관찰 항목은 완주 여부, 막힌 지점, 소요 시간, 수정량, 검색 성공 여부와 재사용 의향으로 시작한다. 목표 수치는 초기 관찰 없이 임의로 확정하지 않는다. 저장 직후 검색은 기능 검증이고, 며칠 뒤 실제로 다시 찾아 쓰는지는 제품 가치 검증이다.

### 작업·보고 단위

```text
사용자 문제 하나 → 화면·기능 변경 → Preview에서 확인 → 결과 기록 → 다음 개선
```

| 보고 항목            | 포함할 내용                       |
| -------------------- | --------------------------------- |
| 사용자에게 달라진 점 | 어떤 일이 더 쉬워졌는지           |
| 실제 작동 범위       | live·mock·미구현 구분             |
| 확인한 경험          | 기기, 새로운 입력 사례, 실제 결과 |
| 남은 문제            | 다음 검증을 막는 항목과 중요도    |

## 10. 후속 작업 경계

- 이 문서는 현황 정리와 개선 제안이며 신규 기능 개발·배포 승인서가 아니다.
- 구현 시 기존 미커밋 변경을 보존하고 프로젝트 폴더 안에서 작업한다.
- 비밀정보 실제 값, 이미지 원본, OCR 개인정보를 문서·로그에 남기지 않는다.
- 제공자 quota 미검증, 공유 Workspace, 개발 자격증명 재사용을 완료된 격리·비용 보장으로 설명하지 않는다.
- 외부 테스트 인원 확대는 현재 팀 내부 테스트와 다른 접근·데이터 경계를 요구한다.
- 현황이 바뀌면 실제 연결 상태와 검증 날짜를 갱신한다. 과거 수치를 최신 실측으로 재사용하지 않는다.
