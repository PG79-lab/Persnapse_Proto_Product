## 0. 먼저 읽을 핵심 결론

**현재 작업물은 명함을 인식·수정·저장하고 제한적으로 다시 찾는 기능형 프로토타입이다. 원본 명세의 맥락 이해·Graph 탐색·분석·행동 제안까지 완결된 인터뷰용 MVP는 아니다.**

| 핵심 항목           | 인계 내용                                                                                                     |
| ------------------- | ------------------------------------------------------------------------------------------------------------- |
| 확보한 자산         | 사용자 확인 후 저장, 독립 인물 식별, 출처·수정 보존, 명함 이미지·연락처, 실제 OCR, 비용 방어, 보호 Preview    |
| 가장 큰 공백        | Preview의 Context 구조화는 mock, Recall은 로컬 규칙·유사도, 실제 분석·행동 제안 미연결                        |
| 원본 대비 주요 누락 | 기본 Graph, 음성 입력·STT, 사용자 피드백·인터뷰 계측                                                          |
| 재현된 문제         | 검색 조건 위반, 상대 날짜 오류, 정확한 OCR 텍스트의 이름·회사 오분류                                          |
| 검증 해석           | 단위 테스트 60개와 기존 Golden 9개가 통과해도 새로운 입력의 품질은 보장되지 않음                              |
| 개선의 중심         | 기반 확장보다 실제 입력 → 정확한 기억 → 탐색·회상 → 근거·행동의 연결                                          |
| 다음 세션의 시작점  | 현재 상태 확인 후 아래 발견 사항을 회귀 테스트로 고정하고, 사용자에게 승인받은 범위의 작은 완결 작업부터 진행 |

### 반드시 유지할 구분

1. **API 연결 시험 성공 ≠ 제품 실행 경로 연결 ≠ 사용자 품질 검증.**
2. **실제 기록이 근거로 존재함 ≠ 그 기록이 질문 조건을 충족함.**
3. **기본 Graph와 Voice를 보류하는 축소 전략 ≠ 원본 필수 범위 충족.**
4. **원본과 다른 구현 ≠ 모두 잘못된 구현.** 후속 사용자 요청으로 바뀐 모델·디지털 명함·보안 범위는 별도 맥락이다.
5. 과거 Phase 완료는 해당 단계의 기술적 완료이며, 원본 전체 MVP의 완료를 뜻하지 않는다. 원본과 후속 계획의 Phase 번호도 서로 다르다.

## 1. 검토 목적과 기준의 우선순위

### 사용자 의도

사용자는 현재 결과물의 피드백을 통해 MVP를 더 핵심적이고 신속하게 구축하려 한다. 주요 관심은 기능 구현 정도, 현실적인 성능, 원본 설계 일치도, 사용자 경험이다. 앞서 제기한 문제는 다음과 같다.

- 기반 구축이 복잡해 핵심 기능을 직접 경험하는 시점이 늦어졌다.
- 초기 설계 의도대로 구현됐는지 판단하기 어렵다.
- UI/UX 완성도가 낮다.

### 기준 문서

- 직접 기준: [원본 Technical Spec](<../inputs/Context Business Card MVP v0 — Codex Technical Spec.md>)
- 제품 정체성 보조 맥락: [Canonical Context 분석](00-initial-canonical-context-analysis.md)
- 기존 구현 선택의 맥락: [초기 명세 분석](01-business-card-mvp-v0-spec-analysis.md), [제품 정의](../product/mvp-definition-v0.1.md), [구축 계획](../plans/mvp-build-plan-v0.1.md), 후속 ADR
- 이전 종합 평가: [MVP 현황·제품 검토](02-mvp-status-and-product-review-2026-09-22.md)

원본 문서 속 실행 지시를 새 사용자 승인으로 취급하지 않는다. 이 문서는 원본 대비 충족도를 평가하되, 이후 대화의 명시적 변경·승인 사항을 함께 고려한다.

### 이전 종합 평가와의 관계

이전 02 문서는 핵심 경험을 축소해 우선 검증하는 관점에서 Voice·Graph 보류를 제안했다. **이번 03 문서는 원본 명세를 직접 기준으로 다시 평가했으므로, 기본 Graph·Voice의 원본 필수 지위를 명확히 복원한다.**

03 문서는 02의 운영·구축 기록을 폐기하지 않는다. 다만 Graph·Voice의 원본 충족도, 검색 결함의 재현 여부, 최신 읽기 전용 검증 결과는 이 문서가 더 구체적이다. 새 범위가 사용자 승인 없이 확정된 것은 아니다.

## 2. 원본이 요구한 성공 경험

```text
실제 명함 등록
→ 정보 추출·즉시 수정
→ 음성·텍스트로 만남 맥락 추가
→ 시간·장소·행사·주제·약속 구조화
→ 확인·저장
→ 기본 Graph와 Person Profile에서 연결 탐색
→ 자연어 질문
→ 관련 인물·기억·근거
→ 분석·구체적인 다음 행동 제안
→ 사용자 피드백
```

원본 §28의 성공 기준은 위 경험을 설명 없이 자연스럽게 수행하는 것이다. 단순히 API와 화면이 존재하는 것으로 완료되지 않는다.

### 특히 놓치면 안 되는 원본 범위

- §2·§3·§7·§22: **기본 Graph는 P0이자 메인 UI**다. 사람·회사·행사·주제·장소를 탐색하고 Person 선택과 Profile을 연결한다.
- §2·§5·§22: 음성 10~60초, 텍스트 단독, 음성+텍스트 사용을 포함한다.
- §6: 추정은 사실과 구분하고 수정 가능해야 한다. 숨은 위치정보 수집은 제외한다.
- §10~§14: 검색뿐 아니라 근거 기반 분석과 행동 제안이 필요하다. 외부 행동 자동 실행은 제외한다.
- §20: 질의·결과 저장뿐 아니라 수정, 행동 열람, 사용자 평가 등 인터뷰 학습이 필요하다.
- §26: 3D, 웹 보강, 애니메이션, 복잡한 연결·점수 등을 먼저 줄인다. 기본 Graph를 단순 장식이나 완전 선택 기능으로 해석하지 않는다.
- §27: 하나의 작동하는 전체 흐름, 실제 API, 최소 추상화와 상호작용 완결성을 우선한다.

2일은 원본의 일정 가정이다. 동일한 범위를 안전하게 2일에 완료할 수 있다는 보장은 없으며, 다음 작업에서 이를 확정 일정으로 재사용하지 않는다.

### 3.3 명함 기능의 추가 경계

- 실제 명함 모습을 보존하고 정보 면에서 전화·메일·웹 링크를 제공한다.
- 업스케일은 Canvas 보간·크기 조정·압축·가벼운 대비 보정이다. AI 글자 복원·초해상도가 아니다.
- 최대 5개 독립 이미지의 대기열은 한 이미지 속 여러 명함 자동 분할과 다르다. 자동 분할은 미구현이다.
- 카메라 크롭은 중앙 고정 비율이다. 자동 테두리 탐지·원근 보정으로 설명하면 안 된다.
- 이 확장은 후속 사용자 요구를 반영한 것으로, 원본에서 벗어났다는 이유만으로 제거하지 않는다.

## 4. 발견 사항 — 재현 결과와 우선순위

여기의 우선순위는 다음 개선 순서를 위한 제안이다. 직전 검토는 코드 수정 없이 수행했으므로 아래 항목은 해결 완료가 아니다.

### F-01. 검색 조건이 맞지 않아도 관련 인물로 반환 — 최우선

**상태: 현재 검색 함수에 대한 합성 실행으로 재현. 실제 사용자 데이터의 오답을 관찰한 것은 아님.**

| 사례 | 질문                                   | 준비한 기록                              | 관측 결과                            |
| ---- | -------------------------------------- | ---------------------------------------- | ------------------------------------ |
| R1   | 지난달 제주에서 만난 양자컴퓨팅 투자자 | 지난달 서울 공장에서 식품 포장 공정 검토 | resolved로 무관한 사람 반환          |
| R2   | 양자컴퓨팅 투자자에게 연락해야 할 사람 | 식품 포장 담당자에게 포장 샘플 전달 약속 | resolved로 무관한 사람 반환          |
| R3   | 오늘 내가 무엇을 해야하지?             | 다음 달 기한의 포장 샘플 전달 약속       | 오늘의 날짜 범위 없이 미래 약속 반환 |

R3는 미래 약속을 오늘 준비하면 안 된다는 판단이 아니다. **'오늘' 조건 자체를 해석·검증하지 않고 결과를 반환한다는 문제**다.

원인:

- 미완료 action 근거에 +28, 시간 조건에 맞는 근거에 +24 등의 가산점이 있다.
- 핵심 장소·주제와 일치하지 않아도 점수 기준을 통과할 수 있다.
- '오늘'은 날짜 범위로 해석되지 않는다.
- '최근/마지막' intent도 존재하지만 검색 순위에서 이를 명시적으로 처리하는 경로는 부족하다. 이 부분은 추가 회귀 검증 대상이다.

영향: 사실인 기록을 잘못된 질문의 답으로 제시하여 '근거로 찾음'이라는 신뢰 신호를 왜곡한다.

제안: 날짜·장소·주제·약속 조건을 분리하고 같은 만남에 연결되는지 확인한다. 부족하면 no_result 또는 추가 조건 확인으로 처리한다. LLM 연결 후에도 근거·조건 검증을 남긴다.

근거: [질의 파서](../../src/domain/recall/query-parser.ts), [순위·응답 생성](../../src/domain/recall/ranker.ts), [corpus 구성](../../src/server/db/recall-repository.ts).

### F-02. 상대 날짜·자유 장소·주제 구조화 실패 — 최우선

**상태: 현재 mock 함수를 합성 입력으로 실행해 재현.**

- 기준 시각: 2026-09-22T03:00:00Z, 한국 시각 9월 22일 12시.
- 입력: '어제 대전에서 만났다. 양자컴퓨팅에 관심이 있다고 했다.'
- 기대: 만남 날짜 9월 21일, 장소 대전, 주제 양자컴퓨팅.
- 결과: 만남 날짜가 기준 시각과 동일, 장소 null, topics 빈 배열.
- 원문은 summary 등에 남는다. 모든 정보가 유실된다는 뜻은 아니다.

명시적 숫자 날짜가 없으면 기준 시각을 그대로 사용하는 처리와 장소·주제 사전 제한이 원인이다. 이 기본 날짜는 inferredFields에 포함되지 않아 확인 필요성이 충분히 드러나지 않는다.

제안: 기존 실제 구조화 어댑터를 연결하고 상대 시간·모르는 값·사용자 수정·필드별 추정 표시를 함께 검증한다. 모델 연결 자체를 수정 완료로 판단하지 않는다.

근거: [mock 구조화](../../src/domain/capture/mock-structurer.ts), [명함 Draft 병합](../../src/domain/business-card/business-card-draft.ts).

### F-03. 정확한 OCR 텍스트에서도 이름·회사 오분류 — 높음

**상태: 합성 General OCR 응답을 앱 분류 함수에 넣어 재현. 유료 Clova 호출이나 이미지 인식 시험 아님.**

| ---- | --------- | --------- |
| 이름 | 김가람    | 가온빛    |
| 회사 | 가온빛    | null      |
| 직책 | 제품 책임 | 제품 책임 |

General OCR 후처리는 회사 패턴, 한글 이름 형태, 글자 높이·순서를 이용한다. 회사명이 패턴에 걸리지 않고 이름보다 크게 인쇄된 사례에서 회사명을 사람 이름으로 선택했다.

제안: OCR 문자 정확도와 필드 배정 정확도를 분리해서 평가한다. 상호·회사 표기, 다양한 배치·언어에서 수정량을 확인하고 애매한 필드는 확인 대상으로 표시한다. 전용 명함 OCR이나 추가 모델 사용은 이 평가와 비용·설정 영향을 확인한 뒤 선택한다.

### 6.1 원본 목표 대비

### 6.2 현재 계측의 문제

- Recall latencyMs는 buildRecallResponse 호출 인자를 만들 때 계산된다. 순위 계산 완료·결과 DB 저장·브라우저 렌더 시간을 모두 포함하지 않는다.
- OCR latencyMs는 runBusinessCardOcr 내부에서 측정한다. 클라이언트 전처리, 요청 전송, 앞선 Storage 업로드, 이후 Draft 저장·표시 전체 시간이 아니다.
- OCR 12초는 provider 실행 timeout이며 촬영부터 결과 표시까지의 최대 보장이 아니다. UI의 '최대 12초' 안내와 구분해야 한다.
- Context의 25초 timeout·최대 2회 시도는 오류 정책이지 5초 UX 목표 달성 근거가 아니다.
- 현재 Recall은 workspace corpus를 읽어 로컬 평가한다. 소규모 성능을 데이터 증가 후 성능으로 일반화하지 않는다. 지금 대규모 확장 설계를 선행할 필요도 없다.

### 6.3 다음 계측 제안

1. 사진 사용 확정 → 수정 가능한 결과 표시.
2. 맥락 제출 → 수정 가능한 구조화 결과 표시.
3. 질문 제출 → 답변·근거 표시.
4. 전체 등록 시간, 수정 필드 수, 입력 중단 지점, 검색 성공 여부.

느린 구간이 확인될 때만 이미지 처리·Storage·DB·provider 시간을 분해한다. Vercel 리전이나 모델 교체를 원인 확인 없이 먼저 수행하지 않는다. 성능 표본은 서로 다른 입력의 단발 측정과 동일 조건의 반복 측정을 구분한다.

### 7.3 합성 반례 재현 조건

직전 반례는 임시 파일 없이 Node·tsx 인라인 실행으로 검증했다. 영구 회귀 테스트 파일은 아직 추가하지 않았다. 실행 시 환경변수 로드·DB·provider가 필요 없는 domain 함수만 사용했다.

**R1~R3 공통:**

- 함수: parseRecallQuery(query, referenceTime), buildRecallResponse(query, parsed, corpus, 1).
- referenceTime: 2026-09-22T03:00:00Z.
- corpus: 한 명만 포함. displayName·normalizedName='검토용 가상인물', headline='식품 포장 담당', organizations=['합성 제조사'].
- documentContent와 interaction evidence text='서울 공장에서 식품 포장 공정 검토'.
- interaction occurredAt=2026-08-15T03:00:00Z, verificationStatus='confirmed'.
- evidence는 합성 id, memoryStatementId·memoryDocumentId=null, interaction actionStatus=null.
- 실제 corpus 구조는 [Recall 타입](../../src/domain/recall/types.ts)을 따른다.

| 사례 | 추가 fixture                                                                                                   | 관측                                    |
| ---- | -------------------------------------------------------------------------------------------------------------- | --------------------------------------- |
| R1   | actions=[]                                                                                                     | 날짜만 맞아도 unrelated 인물이 resolved |
| R2   | pending action '포장 샘플 전달', dueAt=null. 같은 내용을 action_item evidence에도 추가                         | 다른 분야 질문에도 resolved             |
| R3   | pending action '다음 달 포장 샘플 전달', dueAt=2026-10-20T03:00:00Z. 같은 내용을 action_item evidence에도 추가 | dateRange=null로 미래 약속 반환         |

action_item evidence의 occurredAt은 공통 만남 시각이며 actionStatus='pending'이다. actions와 evidence 양쪽을 구성해야 실제 repository의 corpus 생성 방식을 재현한다.

**Context 반례:** structureTextCaptureMock에 F-02의 rawText와 referenceTime을 전달한다. interaction.occurredAt, location, topics, inferredFields를 비교한다.

**OCR 분류 반례:** extractClovaNameCard에 images[0].inferResult='SUCCESS'와 아래 General fields를 전달한다. 각 필드는 lineBreak=true, inferConfidence=1이며 boundingPoly는 너비 200, 표의 높이를 가진 직사각형이다.

| 순서 | inferText         | 높이 |
| ---- | ----------------- | ---: |
| 1    | 가온빛            |   70 |
| 2    | 김가람            |   40 |
| 3    | 제품 책임         |   25 |
| 4    | garam@example.com |   20 |

이는 정확히 읽힌 글자의 분류 시험이다. Clova provider 자체의 문자 인식 정확도·오류율 시험으로 설명하지 않는다.

별도 점검한 '부산에서 만난 사람 누구였지?'와 '서울 강남에서 만나 부산 사업 진출 계획을 논의' 조합은 당시 no_result였다. **그 특정 조합에서 잘못된 인물 반환이 재현됐다고 기록하지 않는다.** 장소 역할·같은 만남 조건의 구분은 여전히 추가 평가 대상이다.

### 유지할 것

- 검토 전 Draft와 확정 Memory의 분리.
- 이름이 같아도 자동 병합하지 않는 독립 Identity와 사용자 확인.
- 사용자 수정, provenance, 원본 입력과 해석의 구분.
- 원자적·멱등 저장, private Storage, 실제 명함 모습과 연락 동작.
- 비밀정보·접근 보호와 DB 기반 OCR 중복·비용 제한.
- 기존 DB·도메인·어댑터와 검증 코드. 전면 재작성은 선행 조건이 아니다.

### 진행 방식에 대한 판단

원본은 빠른 전체 경험을 강조했지만 실제 진행은 기술 기반과 독립 API 검증의 비중이 컸다. 어느 기반 작업이 얼마나 지연시켰는지는 정량화하지 않았다. 보안·비용 대응은 사용자 요청에 따른 작업이므로 그 자체를 불필요한 작업으로 단정하지 않는다.

교정 방향은 안전 기반 폐기가 아니라 **기반 확장을 멈추고 작은 사용자 문제마다 입력·화면·저장·검증을 끝까지 연결하는 것**이다.

## 9. 제안하는 다음 구축 순서

아래 순서는 직전 검토에서 제시한 개선안이다. 현 사용자의 문서 작성 요청을 신규 코드 변경 승인으로 해석하지 않는다.

| 순서 | 범위                                                  | 완료 기준                                                      |
| ---- | ----------------------------------------------------- | -------------------------------------------------------------- |
| 1    | 재현된 검색·날짜 문제 보정, 실제 능력 표시 정정       | 무관한 기록을 맞는 답으로 제시하지 않음. 반례 회귀 테스트 통과 |
| 2    | 기존 실제 Context 구조화 연결 + 등록·검토 흐름 간소화 | 새 명함·자유 메모를 적은 수정으로 저장. 날짜·추정 표시 확인    |
| 3    | 실제 Recall·분석·행동 제안 연결                       | 이름 없는 질의·표현 변화에서 인물·이유·근거·행동이 일치        |
| 4    | 최소 기본 Graph와 연결된 작업 화면                    | Person·Company·Event·Topic·Place 탐색, 선택→Profile 연결       |
| 5    | 10~60초 음성→STT→기존 Context 연결                    | 음성·텍스트 단독 및 함께 사용 가능                             |
| 6    | 실기기 전체 흐름·소수 사용자 관찰                     | 설명 없이 등록→탐색→질문→근거 확인 완주                        |

피드백과 최소 계측은 마지막까지 미루지 않고 2~3번부터 붙인다. '맞는 사람인가', '도움이 됐는가', '어디서 중단했는가'를 기록할 최소 UI·경로부터 시작한다.

### 빠른 구현을 위한 제한

- 기본 Graph는 기존 관계 데이터에서 생성한다. 별도 Graph DB, 3D, 애니메이션, 복잡한 점수는 보류한다.
- Graph 기본 연결·선택·간단하고 설명 가능한 강도 표시를 우선하며, 좁은 화면에 원본 3열 구성을 그대로 강제하지 않는다.
- 이미 정한 모델을 필요한 실행 경로부터 연결한다. 새 범용 Agent framework·provider abstraction을 선행하지 않는다.
- 원본의 제한된 검색·추론 호출 흐름을 유지한다. 새 live 경로에는 timeout·호출 한도·중복 방어를 함께 적용한다.
- OCR 비용 방어가 다른 모델 경로에도 자동으로 적용된다고 가정하지 않는다.
- UI 전면 재디자인보다 등록·확인·탐색의 마찰을 줄인다. 필요하면 기존 컴포넌트를 재배치한다.
- Graph·Voice를 제외하는 전략을 택하려면 '원본 완료'가 아니라 별도의 축소 MVP라고 명시하고 범위를 확인한다.
- '맥락 나중 보완', provider·리전 변경, 외부 테스트 확대는 기존 확정 사항이 아니다. 영향이 큰 변경은 사용자 확인 후 진행한다.

### 새 완료 보고 단위

```text
사용자 문제 하나
→ 필요한 화면·기능만 변경
→ 새 입력과 실패 반례로 검증
→ 승인된 Preview에서 경험 확인
→ 사용자에게 달라진 점·실제 연결 범위·남은 문제 기록
```

저장 직후 검색은 기능 검증이다. 며칠 뒤 다시 필요해 찾아 쓰는지는 제품 가치 검증이므로 분리한다. 근거 없는 성공률 목표나 2일 완성 보장은 추가하지 않는다.
