## 1. 처음 읽을 핵심

제품 목표는 **보유한 정보와 맥락을 상황에 맞게 활용해 사용자의 이해·판단·행동을 돕는 AI 어시스턴트**다. 검색과 리마인드는 이를 위한 기반 기능이며, 제품 가치를 그 두 기능에 한정하지 않는다.

우선 작업 대상은 다음 세 가지다.

1. 대화 맥락 유지: 이전 대화와 사용자 목적을 이어받는다.
2. 검색 안정성: 일부 인덱스 미완성이나 변경에도 정보 활용을 지속한다.
3. 맥락 중심 검색: 인물 요약뿐 아니라 만남·사실·할 일의 근거를 찾아 활용한다.

위 우선순위와 제품 방향은 사용자와 합의했다. 구체적인 스키마, 세션 저장 방식, 검색 알고리즘, 자동 복구 실행 방식은 아직 결정하지 않았다. 이 문서는 구현 지시나 착수 승인을 대신하지 않는다.

## 2. 현재 구현 사실

### 구조 및 파이프라인

- Next.js 기반 단일 풀스택 저장소. UI/features → API → application → domain 및 DB/provider 계층으로 구성된다.
- 화면 기준은 `/` 통합 워크스페이스이며 AI 어시스턴트는 `/#todos`에서 접근한다. 기존 독립 화면을 다시 만드는 방향은 아니다.
- 텍스트 및 검토한 음성 전사 입력 → AI 구조화 초안 → 사용자 검토 및 인물 대응 → 관계형 데이터와 출처 저장 → 검색 문서 재구축 및 임베딩 흐름이 있다. 명함도 OCR·검토 이후 기억 저장 흐름으로 연결된다.
- 확정 데이터와 AI 초안, 저장된 약속·할 일과 생성 제안을 구분하는 기반이 있다.
- live Recall은 검색 준비 확인 → 질문 구조화 → query 임베딩 → 후보 검색 → rerank → 관계형 근거 로드 → 답변 생성·검증 흐름이다. 일반 경로에는 외부 호출 네 단계가 있다.
- 검색 projection은 현재 인물별 `person_profile` 중심이다. 답변에는 후보 인물의 확정된 관계형 근거를 다시 로드한다.
- 답변 검증은 근거 키와 인물 연결, 조건별 근거, 시간 및 같은 만남 조건, 행동 종류 등을 확인한다. 모든 문장의 의미적 타당성을 완전히 증명하는 구조는 아니다.
- 검색 복구 API/UI와 임베딩 상태·재시도 기반이 있다. 일부 정보의 인덱스가 준비되지 않으면 현재 live 검색 전체를 막는다.
- 어시스턴트 화면의 대화 내역은 로컬 UI 상태다. Recall 요청은 현재 질문과 기준 시간을 보내며 이전 대화를 전달하지 않는다. DB의 질문 이력 저장과 대화 맥락 활용은 별개다.
- 기록, 검색, 브리핑 기능은 존재하지만 하나의 대화 흐름에서 의도에 따라 연결하는 범용 어시스턴트 구조는 아직 제한적이다. 외부 행동을 자동 실행하지 않는다.

### 현재 문제와 개선 필요성

| 구분      | 문제                                                  | 영향                                                  |
| --------- | ----------------------------------------------------- | ----------------------------------------------------- |
| 대화      | 이전 질문·답변, 선택한 인물과 목적을 이어받지 못함    | 대명사와 후속 질문 처리, 지속적인 작업 지원이 어려움  |
| 안정성    | 일부 인덱스 미준비가 전체 검색을 막음                 | 일부 실패나 기록 변경이 전체 사용 흐름을 끊을 수 있음 |
| 검색 단위 | 인물 요약 중심 후보 검색                              | 개별 만남·사실·할 일의 세부 맥락을 찾는 데 한계       |
| 정보 활용 | 검색·기록·브리핑이 분리됨                             | 맥락 연결, 판단 지원, 행동 준비의 경험이 제한적       |
| 응답 품질 | 다단계 외부 호출 및 의미 검증의 한계                  | 지연·실패와 근거 해석 오류를 관리해야 함              |
| 평가·운영 | 실제 사용 사례 평가와 호출별 비용·지연 관리 보강 필요 | 개선 효과와 제품 품질을 일관되게 확인하기 어려움      |

## 3. 합의한 제품 방향

### 입력에서 보존해야 할 정보

다양한 Input, 주로 텍스트에서 명확한 주요 사실과 맥락을 추출하고 시간·인물·관계와 대응시키는 것이 중요하다.

- 사실: 누가 무엇을 말하거나 했는지, 약속·할 일·기한이 무엇인지.
- 맥락: 언제, 어떤 만남·상황에서, 누구와 관련해 나온 정보인지.
- 근거: 원문 입력, 출처, 사용자 확인 상태, 불확실하거나 해석이 필요한 부분.

예: “지난 금요일 민수와 전시회에서 만났고 다음 주에 소개서를 보내기로 했다.”
인물, 전시회 만남, 만남 날짜, 소개서 전달 약속, 기한, 원문 근거를 연결해야 한다. 상대 날짜를 정규화할 때는 입력의 기준 시점과 불확실성을 다뤄야 한다. 정확한 처리 계약은 설계에서 정한다.

현재 구조화 기반을 활용하되, 필요한 맥락이 충분히 보존되는지 확인한다. 모든 입력 수단을 새로 만들거나 데이터 모델을 전면 교체하기로 결정한 것은 아니다.

### 어시스턴트가 제공할 가치

| 역할          | 가치                                        | 대표 예시                                               |
| ------------- | ------------------------------------------- | ------------------------------------------------------- |
| 이해·정리     | 흩어진 정보에서 상황과 흐름 정리            | “민수와 진행 중인 이야기를 정리해줘.”                   |
| 연결·해석     | 기록 사이의 관계·변화·공통점 설명           | “이전에 말한 관심사와 이번 제안이 어떻게 연결돼?”       |
| 판단 지원     | 목적에 맞는 우선순위·선택지·고려사항 제공   | “이번 주 누구에게 먼저 연락하면 좋을까?”                |
| 행동 준비     | 맥락을 반영한 미팅 준비·질문·연락 초안 제공 | “다음 만남에서 이어갈 이야기와 확인할 사항을 준비해줘.” |
| 검색·리마인드 | 필요한 사실과 약속을 빠르게 회상            | “민수에게 보내기로 한 자료가 뭐였지?”                   |

이 예시는 제품 방향을 설명한다. 모두를 이번 첫 구현 범위에 넣기로 확정한 것은 아니다.

### 설계·UX 원칙

- 대화 맥락과 저장된 기록의 맥락을 구분하고 연결한다.
- 현재 사용자 목적에 필요한 맥락을 골라 활용한다. 많은 정보를 무조건 전달하는 것이 목표가 아니다.
- 확인된 사실, 어시스턴트의 해석, 제안을 구분한다.
- 원문 근거와 확인 상태를 유지하고 서로 다른 만남을 섞어 사실을 만들지 않는다.
- 모호하거나 근거가 부족하면 확인한다. 정보가 없다는 것과 아직 검색되지 않았다는 것을 구분한다.
- 필요한 결과를 먼저 보여주고 근거와 다음 행동을 이어서 제공한다.
- 생성 제안을 저장된 약속처럼 표현하지 않는다. 외부 행동 실행 범위는 별도 결정한다.

## 4. 우선 작업 범위와 미결정 사항

| 우선순위          | 합의한 방향                                                    | 아직 설계할 사항                                                                  |
| ----------------- | -------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 1. 대화 맥락      | 최근 대화·선택 인물·시간 범위·현재 목적 유지, 모호한 지시 확인 | 세션 저장 위치와 수명, 맥락 요약, 참조 해석, 사용자 수정·초기화 UX                |

평가 후보는 후속 질문의 대상 유지, 서로 다른 만남 구분, 약속과 제안 구분, 일부 인덱스 실패 시 부분 답변, 수정한 기록 반영, 근거 기반 정리·판단 지원이다. 정량 목표와 검증 방법은 미확정이다.

## 6. 동시 작업 공간 탐색 결과 및 제안

### 확인된 상태

- 등록된 Git worktree는 `D:\Persnapse\persnapse-mvp` 하나이며 브랜치는 `main`이다.
- 프론트 통합, 문서, 검증 스크립트, E2E 등에 미커밋 변경 및 삭제가 있다. 미추적 명함 인계 문서도 있다.
- 이번 문서 외에 기존 변경은 수정하지 않았다. worktree·브랜치 생성, 커밋, stash는 하지 않았다.
- 다른 세션의 실행 프로세스, 포트, 사용 중인 원격 DB는 조사하지 않았다. 실제 실행 자원 충돌 여부는 착수 시 확인해야 한다.

### 권장 공간: 별도 Git worktree + 전용 브랜치

- 작업 경로 후보: `D:\Persnapse\worktrees\persnapse-ai-assistant`
- 브랜치 후보: `feat/ai-assistant-context`
- 이 경로와 브랜치는 제안이며 아직 생성하지 않았다.
- 같은 폴더에서 브랜치만 바꾸는 방식은 동시 세션의 파일과 체크아웃 상태를 공유한다. 별도 worktree로 파일 작업을 분리한다.
- worktree는 Git 이력을 공유하지만 작업 파일·인덱스는 분리된다. 나중에 같은 파일을 통합하면 병합 충돌은 여전히 가능하다.

### 착수 전 반드시 정할 기준 코드

worktree에는 현재 폴더의 미커밋 변경이 자동으로 포함되지 않는다. 현재 HEAD만으로 시작하면 이번 분석에서 본 프론트 변경 등이 빠질 수 있다.

1. 다른 세션과 최신 변경의 소유권 및 준비 상태를 확인한다.
2. 필요한 변경이 반영된 합의된 커밋을 기준으로 worktree를 만든다. 다른 세션의 변경을 임의로 커밋·stash하지 않는다.
3. 커밋 전 착수가 필요한 경우에는 포함할 변경과 검토 가능한 스냅샷 방식을 별도로 정한다. 현재 미커밋 변경을 통째로 복사하는 것으로 해결했다고 간주하지 않는다.
4. 기준 커밋과 포함·제외 범위를 작업 인계에 기록한다. 이 문서도 기준 커밋에 포함하거나 명시적으로 전달한다.

### 파일 및 실행 자원 경계

- AI 작업의 주요 수정 후보는 위 코드 탐색 표의 Recall/UI/검색 계약과 관련 테스트다. 아직 파일 소유권을 확정한 것은 아니다.
- `assistant.tsx`, 공통 워크스페이스 UI, capture repository, 공통 스키마·migration, 환경 설정, package/lockfile은 다른 작업과 겹칠 수 있어 변경 전에 조율한다.
- 인접 기능으로 연결해야 하면 변경 파일과 계약을 먼저 공유하고, 통합은 합의된 기준에서 진행한다.
- 전용 의존성·빌드 출력·테스트 출력과 다른 개발 서버 포트를 사용한다. 예시 포트는 3100이며 사용 가능 여부는 확인 전이다. 동일 폴더의 `.next`를 공유하지 않는다.
- Git worktree는 원격 DB·Storage·AI 비용을 격리하지 않는다. 테스트 DB 또는 별도 workspace ID와 격리된 테스트 데이터, mock 기본 실행 정책을 정한다. 전역 스키마 변경은 별도 workspace ID만으로 격리되지 않으므로 독립 DB/브랜치에서 검증한다.
- `.env`는 worktree에 자동 전달되지 않는다. 필요한 설정은 별도로 구성하고 비밀 값을 문서나 Git에 넣지 않는다.
- E2E가 기본 포트·DB에 연결되는지 착수 시 확인한다. 각 세션의 프로세스만 종료한다.

## 7. 새 세션에 전달할 지시

> 이 문서와 AGENTS.md를 먼저 읽고 실제 코드 상태를 대조한다. 현재는 방향 구체화 단계이며 구현 승인이 없다. 대표 사용 사례, 우선 1~3단계의 설계와 완료 기준을 사용자와 정리한다. 명시적 OK 후 합의된 기준 커밋에서 AI 전용 worktree로 구현한다. 다른 세션의 미커밋 변경은 수정·커밋·stash하지 않는다. 대화 맥락과 기록 맥락, 사실과 해석·제안, 파일 격리와 DB·실행환경 격리를 구분한다.

이번에는 문서 작성과 정적 코드 확인만 수행했다. 테스트·빌드·live AI 호출·원격 데이터 검증 결과를 새로 확보한 것은 아니다.
