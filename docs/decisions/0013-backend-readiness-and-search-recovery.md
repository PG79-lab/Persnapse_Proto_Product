# ADR 0013 — 프론트 연결 전 검증과 명시적 검색 준비 복구

- 날짜: 2026-10-07
- 상태: 구현. 로컬 검증 결과와 원격 연결 장애는 [검증 기준점](../handoff/2026-10-07-backend-readiness.md)에 별도 기록한다.
- 요청: 기존 UI의 백엔드 연결을 진행하되, 먼저 문제를 검증·해결하고 제품 설계와 방향성을 보존한다.

## 제품 기준

Persnapse의 중심은 `Capture → Context → Memory → Recall → Action`이다. 명함·녹음은 관계 맥락을 남기는 입력 수단이며, 일정·업무 UI는 저장된 약속과 후속 행동으로 연결한다. 신뢰할 수 있는 사람과 근거를 다시 찾는 가치를 유지한다.

- 사용자 확인 전 Draft와 확인 후 Memory를 구분한다.
- 기존 인물 선택이나 신규 생성은 사용자가 결정한다. 이름만으로 병합하지 않는다.
- 사용자 수정, 발생 시점, 원문 출처를 보존한다.
- PostgreSQL이 원본이며 그래프와 검색 문서는 재생성 가능한 projection이다.
- 저장된 약속과 AI 제안을 구분하며 메일·외부 캘린더를 자동 실행하지 않는다.
- 기본 Graph와 Voice의 원래 범위를 유지하되, Capture/Recall 연결의 선행 조건으로 만들지 않는다.

근거: [제품 정의](../product/mvp-definition-v0.1.md), [시스템 설계](../architecture/mvp-architecture-v0.1.md), ADR 0002·0003·0006·0007·0011·0012. 최신 사용자 요청의 업무별 UI 구성을 유지하며, 기존 문서의 과거 모델 이름·배포 검증을 현재 접근 가능성의 증거로 사용하지 않는다.

## 연결 방향과 검증 순서

기존 Next.js 애플리케이션에 UI를 단계적으로 연결하고 Supabase를 공통 원본으로 사용하는 방향을 유지한다. 이번 변경은 해당 통합의 준비 단계다. `koin-contact-map`의 프론트 구현과 공유 배포를 수정하지 않는다.

1. 읽기 전용 연결·워크스페이스·schema·RLS·migration·명함 이미지 bucket 점검.
2. 기존 Capture/OCR/Review/Identity/Commit 계약의 DB 수직 검증.
3. 검색 문서 상태 확인과 필요한 문서만 제한적으로 준비, Recall 검증.
4. 통과 후 인맥·만남·일정·그래프 UI 연결. 전사·브리핑·메일 초안은 별도 작업으로 연결.

기존 로컬 UI 저장소와 Supabase를 각각 원본으로 유지하지 않는다. 프론트 ID와 서버 UUID, 명함 base64 입력과 multipart 계약, 인물 없는 업무와 기존 `action_items.person_id` 필수 조건은 실제 통합 전에 해결할 계약 차이다. 샘플·실제 데이터의 자동 이관이나 seed 재실행은 이번 변경에 포함하지 않는다.

## 검색 복구 결정

ADR 0011의 전체 live 검색 준비 조건을 유지한다. 일부 문서가 누락된 상태에서 `no_result`를 반환하지 않는다.

- `GET /api/recall/preparation`: 기본 워크스페이스의 준비 수와 재시도 가능 상태만 조회한다. 모델 호출·projection 쓰기 없음.
- `POST /api/recall/preparation`: 사용자가 명시적으로 요청할 때 재시도 가능한 인물 최대 2명을 순차 처리한다. Voyage embedding 요청 최대 2회이며 자동 반복이나 답변 생성 없음.
- 현재 모델과 일치하는 `ready` 상태이면서 vector가 실제 존재해야 준비 완료다. `ready`에 null vector가 있는 문서도 복구 대상으로 취급한다.
- 활성 처리 lease를 재요청하지 않는다. 2분이 지난 lease와 실패·미준비 문서는 재시도할 수 있다. 실패 횟수·최근 처리 시각으로 순서를 분산하여 같은 실패 문서가 뒤의 작업을 계속 가로막지 않게 한다.
- 기존 atomic claim과 content hash 검증을 유지한다. 변경 전 내용으로 생성된 embedding을 반영하지 않으며, 확정된 원문·기억 저장을 되돌리지 않는다.
- mock 모드는 모델 호출과 검색 문서 재작성을 하지 않는다.
- 기존 workspace 단기 호출 제한을 사용한다. 일/월 누적 한도를 다시 도입하지 않는다.

화면은 `SEARCH_NOT_READY` 오류 이후에만 상태를 조회한다. 사용자가 배치를 재시도하며, 완료 후에도 검색 버튼을 다시 눌러야 한다. 입력 초안과 진행 상황을 보존하고 중복 클릭을 차단한다. 이미 다른 세션에서 준비를 끝냈다면 상태 재조회만으로 준비 완료를 확인할 수 있다.

## 운영 경계와 한계

- 기존 localhost/보호된 Vercel Preview 접근 정책과 서버 전용 키 경계를 그대로 사용한다.
- 클라이언트가 전달하는 workspace/person ID를 복구 대상으로 사용하지 않는다.
- 실패 응답에는 DB 주소·키·제공자 원문 오류를 노출하지 않는다. 상태 응답은 `private, no-store`다.
- 새 `npm run db:preflight`는 DNS와 DB를 읽기 전용으로 확인한다. schema 초기화·seed·indexing·AI 호출을 하지 않는다. 키 값은 출력하지 않는다.
- 단위 테스트의 SQL 대역은 실제 PostgreSQL 통합 검증을 대신하지 않는다. 브라우저의 합성 응답은 모델 품질이나 실제 응답 속도를 증명하지 않는다.
- 전역 HTTP 요청 멱등성과 작업 큐는 추가하지 않는다. 서버 함수 중단·provider timeout 시 확정 기억은 유지되며 검색 상태 재확인 후 명시적 재시도가 필요하다.
