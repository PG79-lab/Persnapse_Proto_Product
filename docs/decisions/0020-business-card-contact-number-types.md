# 0020. 명함 연락처 번호 종류 보존

- 날짜: 2026-10-12
- 상태: 구현·검증 완료, 실촬영 평가 대기
- 작업 화면: 통합 워크스페이스 `/#cards`

## 문제와 목표

사용자가 실제 명함에서 숫자는 잘 추출되지만 전화·휴대폰·팩스 구분이 사라지는 문제를 보고했다. 기존 `identity.phones: string[]`에는 번호 종류를 담을 수 없었고, CLOVA Name Card의 `mobile`과 `tel`은 하나로 합쳐지고 `fax`는 버려졌다.

목표는 숫자와 함께 명함에 인쇄된 표기를 보존하고 번호의 의미를 구분하는 것이다. 원본 명함 이미지 복원과 관계 기억 저장 경계는 기존 설계를 따른다.

## 결정

| 항목        | 적용 내용                                                                                                                   |
| ----------- | --------------------------------------------------------------------------------------------------------------------------- |
| 구조        | `identity.contactNumbers: [{ type, value, rawLabel }]`, 최대 8개                                                            |
| 종류        | `phone`(전화), `mobile`(휴대폰), `fax`(팩스), `unknown`(미분류)                                                             |
| 표기        | `rawLabel`에 `Tel`, `Fax`, `HP`, `H.P.` 등의 인식 표기를 보존. 표기가 없으면 `null`                                         |
| 표기 분류   | 대소문자·전각·약어의 마침표 차이를 처리. `Tel/T/Phone/전화/직통`, `Mobile/M/HP/H.P./H/P/Cell/휴대폰`, `Fax/F/팩스` 지원     |
| 불확실성    | 표기 없음·알 수 없는 표기·`Tel/Fax` 같은 복합 표기는 미분류. `010`이나 국가 코드만으로 종류를 추정하지 않음                 |
| 중복        | 같은 종류·같은 숫자는 합침. 동일 번호가 전화와 팩스로 각각 명시된 경우 두 종류를 유지                                       |
| 기존 호환   | v1 초안은 추가 필드를 선택형으로 읽음. 새 구조가 있으면 `phones`를 재계산하여 알려진 팩스를 제외. 과거 번호는 미분류로 표시 |
| API 호출    | 기존 OpenAI 이미지 추출 1회에서 종류·숫자·표기를 함께 반환. 추가 분류 LLM 호출 없음                                         |
| 사용자 수정 | 전화·휴대폰·팩스·미분류 입력란으로 구분. 번호를 해당 입력란으로 옮겨 수동 수정 가능                                         |
| 표시        | OK 이후 결과와 인맥 프로필의 명함별 연락처에 종류·번호·원문 표기를 표시                                                     |

### 제공자별 처리

- **OpenAI:** 이미지 안의 같은 행 또는 명확히 정렬된 표기/번호 쌍을 함께 읽도록 지시한다. 모델이 반환한 종류가 표기와 모순되면 서버의 표기 규칙을 적용한다. 표기 없이 모델이 휴대폰으로 추측한 결과는 미분류로 낮춘다. JSON 구조 검증은 내용 정확도 보장이 아니므로 실제 인식 평가는 별도로 필요하다.
- **CLOVA Name Card:** 제공자가 이미 구분한 `mobile`, `tel`, `fax`를 각각 보존한다. 이 응답에는 실제 인쇄 표기가 없으므로 `rawLabel`은 `null`로 둔다.
- **CLOVA General:** 기존 OCR 행을 사용해 번호 바로 앞 표기를 연결한다. 바로 이전 행이 표기만으로 이루어진 경우에도 연결한다. 다른 연락처 행으로 표기가 번지지 않도록 한다. 복잡한 다단 레이아웃의 정확도는 실제 사진으로 추가 검증해야 한다.

OpenAI 출력 형식은 [OpenAI Docs: Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)의 필수 키·중첩 객체·`additionalProperties: false` 규칙을 따른다.

### 저장과 인물 일치 판단

- 번호 종류와 원문 표기는 기존 초안 JSON과 `business_cards.card_data` JSON에 보존한다. 새 DB 컬럼이나 마이그레이션은 필요 없다.
- 일반 인맥 연락처의 기존 `person_attributes.kind='phone'`에는 전화·휴대폰·미분류 번호를 저장한다. 이 기존 속성 자체는 번호 종류를 세분화하지 않는다. 종류의 기준은 명함별 `card_data.contactNumbers`이며 통합 프로필에서 이를 보여준다.
- 알려진 팩스는 일반 전화 속성과 전화번호 기반 인물 일치 판단에서 제외한다. 팩스 데이터는 명함 JSON에 남는다.
- 과거 종류 없는 추출 캐시는 새 업로드의 OCR 결과로 재사용하지 않는다. 이미 확인·저장된 과거 명함을 자동으로 다시 OCR하지 않는다.

## 검증 방법과 제한

1. 약어·전각·국제번호·내선·복합 표기·표기 누락·같은 행의 여러 번호를 회귀 테스트한다.
2. 숫자 일치와 `종류+숫자` 일치를 각각 평가하여 숫자는 맞고 종류가 틀린 경우를 식별한다.
3. 통합 UI에서 종류별 수정 → OK → 재개 → 인맥 프로필 표시를 검증한다.
4. DB·Storage 검증에서는 합성 데이터를 저장하고 팩스 제외·종류 보존·프로필 투영을 확인한 뒤 생성한 시험 데이터를 정리한다.
5. `npm run ai:verify:card-numbers`는 합성 이미지 2장을 실제 OpenAI에 전송한다. 유료 호출이며 실제 명함의 성능 기준이 아니다.

실제 촬영 명함과 정답 라벨은 아직 제공되지 않았다. 이 변경만으로 실명함 분류 정확도나 처리 지연 개선을 확정하지 않는다. 추가 API 호출은 없지만 출력 필드 증가가 실제 응답 시간에 주는 영향은 측정해야 한다.

DB 검증에서 `card_data`가 JSON 문자열로 반환되는 경우를 확인했다. 통합 워크스페이스 조회도 기존 개별 프로필 조회와 동일하게 JSON을 해석·검증하도록 보완했다. 실패했던 DB 시험 역시 생성한 DB 행과 Storage 객체가 0건 남았음을 확인했다.

변경은 로컬 작업 트리에 적용했으며 새 Preview 배포나 커밋은 수행하지 않았다. 기존 명함은 자동 재인식하지 않으므로 새 추출을 확인하려면 사진을 다시 업로드해야 한다.
