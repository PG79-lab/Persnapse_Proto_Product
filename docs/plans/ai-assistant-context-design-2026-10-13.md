- 작성일: 2026-10-13
- 상태: 사용자 승인 후 핵심 구현 진행. 아래 내용은 최초 설계 기준이며 모든 정량 목표의 달성을 의미하지 않는다. 현재 구현·검증 경계는 [구축·통합 인계](../operations/ai-assistant-implementation-2026-10-13.md)를 참고한다.
- 선행 합의: [제품 방향 및 세션 인계](../handoff/ai-assistant-direction-2026-10-13.md)

- 구현 조건: 사용자가 범위·완료 기준을 검토하고 명시적으로 OK한 뒤 전용 worktree에서 착수한다.

## 1. 목표와 사용자 경험

**보유한 정보와 맥락을 적재적소에 활용해 사용자의 이해·판단·행동 준비를 돕는다.** 대화 유지, 검색 안정성, 세부 맥락 검색을 하나의 사용자 경험으로 연결한다.

| 목표                  | 사용자가 경험할 결과                                                                                                        |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 대화의 연속성         | 인물·주제·기간을 반복 입력하지 않고 후속 질문을 이어간다. 모호하면 짧게 확인한다.                                           |
| 정보 활용의 지속성    | 일부 검색 인덱스가 준비 중이어도 찾을 수 있는 기록으로 답변받는다. 수정한 사실을 오래된 임베딩 때문에 잘못 안내받지 않는다. |
| 정확한 맥락 연결      | 인물, 만남, 발언·사실, 약속, 기한을 구분해 정리하고 서로 관련된 기록을 연결한다.                                            |
| 상황에 맞는 가치 제공 | 관계 진행 상황을 이해하고, 우선순위를 판단하며, 다음 만남의 질문과 준비 사항을 얻는다.                                      |
| 근거와 통제           | 사실·해석·제안을 구분하고 근거를 펼쳐 볼 수 있다. 대화의 대상·기간을 수정하고 새 대화를 시작할 수 있다.                     |

### 대표 사용 사례와 기대 결과

| ID  | 대화 또는 상황                                              | 기대 결과 및 실패 조건                                                                                                  |
| --- | ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| U1  | “민수와 최근 무슨 얘기 했지?” → “그때 내가 보내기로 한 건?” | 직전 답변에서 특정된 민수와 만남을 이어받는다. 여러 만남이 제시됐다면 어느 만남인지 확인한다.                           |
| U2  | “전시회에서 만난 사람은?” → “그 사람에게 연락 준비해줘.”    | 여러 후보면 선택을 요청한다. 임의로 첫 후보를 선택하지 않는다.                                                          |
| U3  | “이번 주 약속은?” → “지난달 만남 기준으로 다시 봐줘.”       | 최신 지시로 범위를 바꾼다. 약속 기한과 만남 날짜를 서로 다른 조건으로 유지한다.                                         |
| U4  | 일부 인물의 임베딩 실패 또는 수정 직후 질문                 | 최신 관계형 기록·키워드 검색을 활용한다. 빠진 검색 범위가 있으면 표시하고 전체 결과인 것처럼 표현하지 않는다.           |
| U5  | “민수와 진행 중인 이야기를 정리해줘.”                       | 관련 만남, 주요 사실, 미완료 약속을 시간 흐름과 함께 정리한다. 서로 다른 만남을 한 번의 사건처럼 합치지 않는다.         |
| U6  | “이전 관심사와 이번 제안이 어떻게 연결돼?”                  | 두 기록을 근거로 연결점을 설명한다. 해석을 사실로 저장하거나 표현하지 않는다.                                           |
| U7  | “이번 주 누구에게 먼저 연락하면 좋을까?”                    | 확인된 미완료 약속·기한과 사용자 목적을 바탕으로 우선순위 및 이유를 제시한다. 개인 친밀도 등 없는 정보를 만들지 않는다. |
| U8  | “민수와 다음 만남을 준비해줘.” → “질문 세 개로 줄여줘.”     | 근거 기반 요약·확인 질문·준비 사항을 만든 뒤 결과 형식을 바꾼다. 보내거나 저장하지 않는다.                              |
| U9  | 기록 수정·삭제, 대화 새로고침·초기화                        | 세션은 복원되지만 사실은 현재 DB에서 다시 확인한다. 새 대화에는 이전 지시와 대상이 섞이지 않는다.                       |
| U10 | 관련 기록 없음, 동명이인, 서로 충돌하는 기록                | 각각 미발견·대상 확인·기록 불일치로 구분한다. “최근 기록”만을 이유로 진실을 임의 확정하지 않는다.                       |

## 2. 이번 구현 범위

### 포함 제안

- 서버 저장형 대화 세션, 후속 질문의 대상·기간·사용자 목적 유지, 확인 질문과 선택 처리.
- 검색 준비의 전역 차단 제거, 최신 관계형 기록 기반 fallback, 검색 범위·제한 표시.
- 인물 요약과 별도로 만남·개별 사실·할 일 단위 검색 projection 및 하이브리드 검색.
- 입력 저장에서 기존 사실·맥락·출처 연결이 검색과 답변까지 보존되는지 점검하고 필요한 누락만 보완.
- 답변 모드: 조회, 상황 정리, 기록 연결·비교, 우선순위 판단 지원, 미팅·연락 준비용 초안.
- 근거 선택·검증, 구조화된 사실/해석/제안 표시, 단계별 지연·호출·검색 품질 평가.
- 변경 이벤트에 따른 durable indexing job, 제한된 자동 재시도와 수동 복구.

### 후속 후보

대화로 기억·업무를 생성·수정하는 실행 도구, 외부 메시지 발송, 자율 행동, 먼저 알림을 보내는 기능, 새 Input 채널, 전체 입력 추출 모델 재설계, 장기 개인 선호 학습, 범용 관계 그래프 추론은 이번 완료 범위에서 제외한다. 기존 기록 진입·인물 보기·할 일 보기 연결은 유지한다.

세션은 현재 프로토타입 workspace 접근 경계 안에서 설계한다. 개인 인증·사용자별 권한 체계 완성은 별도 범위이며, 인증 없는 현 구조에서 다른 사람의 세션까지 열람하는 UI는 제공하지 않는다.

## 3. 기술 구조

기존 Next.js, PostgreSQL, 현재 AI provider adapter를 유지한다. 이번 개선을 위해 별도 벡터 DB나 범용 에이전트 프레임워크를 도입하지 않는다.

```text
현재 질문 + sessionId + 명시적 대상/기간 선택
  → 세션 로드 및 참조 해석
  → 목적·대상·시간·조건 계획 / 필요하면 확인 질문
  → 구조화 검색 + 키워드 검색 + 준비된 벡터 검색
  → 후보 병합·재정렬
  → 최신 관계형 근거 로드 및 제한된 맥락 확장
  → 사실·해석·제안 또는 준비 초안 생성
  → 근거·조건·범위 검증
  → 결과·유효한 대화 상태 저장 및 표시

확정 기록 변경
  → 같은 DB transaction에서 검색 unit 갱신·무효화 + job 등록
  → 별도 worker가 임베딩 실행
  → hash/version/lease 조건 확인 후 ready 전환
```

### 3.1 대화 세션과 참조 해석

추가 테이블 제안:

| 테이블               | 핵심 필드 및 책임                                                                                                   |
| -------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `assistant_sessions` | workspace_id, id, version, 목적, 명시적 대상·기간, 보류 중 확인 질문, 요약 상태, 마지막 활동·만료 시각              |
| `assistant_turns`    | workspace_id, session_id, turn 번호, request_id, payload_hash, 입력, 상태, 최종 응답, 선택 근거 키, 시간, 오류 코드 |

- workspace 복합 FK와 접근 정책을 적용하고, API에서 workspace는 서버가 결정한다. 세션 ID는 추측하기 어려운 값으로 생성한다. 개인 인증을 대체한다고 보지 않는다.
- 세션 ID만 브라우저에 보관하고 본문은 서버에 저장한다. 새로고침 시 현재 세션을 복원하며 다른 브라우저로 자동 공유하지 않는다.
- v0.1 기본값 제안: 7일 미사용 시 맥락 만료, 대화 보존 최대 30일. 만료 확인은 접근 시, 본문 정리는 별도 cleanup으로 수행한다. 기간은 승인 시 조정 가능하다.
- 모델 입력은 최근 최대 6개 완료 turn과 압축된 목적·대상·기간을 사용한다. 세션 요약은 연산용 상태이며 사실 DB에 저장하지 않는다.
- 초기 구현의 요약은 구조화된 상태 갱신으로 만들고 추가 요약 LLM 호출을 늘리지 않는다. 검증된 응답의 제한된 결과와 사용자 요청을 이어받는다.
- 모델이 지목한 인물·만남 ID는 현재 workspace와 DB에 존재하는지 검증한다. 여러 후보에서 하나를 자동 선택하지 않는다.
- 우선순위는 최신 사용자 명시 지시 → 사용자의 대상 선택 → 직전의 단일 검증 대상 → 기존 세션 상태다. 불일치·다중 후보는 확인 질문으로 해소한다.
- 별도 화면에서 인물 프로필을 열었다는 이유만으로 대화 대상을 바꾸지 않는다. “이 인물로 대화”처럼 명시적으로 연결한다.
- 대화에 제시한 사실을 다음 turn의 진실로 재사용하지 않는다. 관련 근거를 DB에서 다시 읽고 삭제·수정 여부를 확인한다.
- “질문 세 개로 줄여줘” 같은 결과 편집은 직전 유효한 결과를 재사용할 수 있으나 근거 갱신을 확인한다. 새로운 사실 주장이나 판단에는 다시 검색한다.

#### 요청·재시도·동시성

POST `/api/assistant/turns` 제안: `{ sessionId?, requestId, expectedVersion?, message, contextSelection? }`. 선택 데이터는 personId, interactionId, 기간 등 허용된 타입만 받으며 모두 서버에서 검증한다.

- 짧은 transaction에서 세션 버전·busy lease와 request ID를 확인하고 turn을 예약한다. 모델 호출 동안 DB lock을 유지하지 않는다.
- 같은 request ID와 같은 payload는 처리 상태 또는 저장된 응답을 반환한다. 다른 payload면 409로 거절한다.
- 같은 세션의 동시 turn은 409 및 갱신 안내로 직렬화한다. 버전과 lease token을 최종 저장 시 다시 확인해 늦은 응답이 새 맥락을 덮어쓰지 않게 한다.
- 처리 lease는 요청 전체 timeout보다 길게 두며 v0.1은 90초 제안이다. 만료된 처리 turn은 결과 불명으로 표시한다. 결제된 호출인지 알 수 없으므로 자동 재실행하지 않는다.
- 네트워크 유실 후에는 상태 조회로 복구한다. worker crash까지 포함한 외부 호출의 exactly-once는 보장하지 않는다.
- 실패 turn은 이력에 남기되 유효한 세션 맥락에 반영하지 않는다. 새 대화는 새 session을 만든다.

GET `/api/assistant/sessions/:id`와 turn 상태 조회를 제공한다. 기존 `/api/recall`은 대화 없는 기존 계약을 유지하며 내부 검색 서비스를 공유한다. 기존 피드백의 queryId 연결도 유지한다.

### 3.2 목적과 답변 계약

기존 `lookup/action/analysis` 계획을 내부 목적 `lookup/summarize/connect/prioritize/prepare`로 확장한다. 자유로운 tool 실행 대신 검증 가능한 읽기 전용 작업 흐름을 둔다.

- plan: 목적, 검증된 대상 ID, 질문 조건, 만남 날짜 범위, 할 일 기한 범위, 같은 만남 조건, 사용자 목적, 원하는 결과 형식, 확인 질문.
- 최근 사용자 지시가 없는 조건을 이전 세션에서 무조건 끌어오지 않는다. 재사용한 대상·기간은 응답 UI에서 확인·수정할 수 있게 한다.
- 시간은 Asia/Seoul로 정규화한다. 서버 기준 시각을 기본으로 하고 과거 turn의 “오늘”을 새로운 turn에 그대로 적용하지 않는다.
- API 응답은 기존 Recall 결과를 포함하는 버전 명시 envelope로 제공한다: session/version/turn, status, answer mode, sections, evidence, coverage, available next steps.
- sections는 `fact/interpretation/suggestion/draft` 유형과 근거 키를 갖는다. 주요 주장 단위로 지원 근거를 연결하고 단순 키 존재 검증과 의미 검증의 한계를 구분한다.
- `resolved/ambiguous/no_result`에 `insufficient_context`를 새 어시스턴트 계약으로 추가한다. 검색 제한은 status와 분리된 coverage로 표현한다.
- 우선순위는 기한·미완료 약속·사용자가 명시한 목적을 설명 가능한 기준으로 삼는다. 전체 목록을 구조화 조회하지 않았다면 “전체 최우선”이라고 주장하지 않는다.
- 답변은 선택된 근거 안에서 생성한다. 준비 초안에는 기록에 없는 확인 질문을 제안할 수 있으나 새 사실처럼 쓰지 않는다.

### 3.3 세부 기억 검색 projection

**새 `memory_search_units` 테이블을 제안한다.** 현재 `memory_documents`의 인물 projection과 처음부터 합치지 않는다. 최신 인물 재구축 함수에는 인물 archive 시 해당 인물의 문서를 모두 삭제하는 경로가 있어, 만남의 여러 참가자와 세부 문서 생명주기를 함께 넣으면 위험하다.

| unit 종류        | 원본 및 책임                                                                           |
| ---------------- | -------------------------------------------------------------------------------------- |
| person           | 기존 인물 projection/확정 프로필. 넓은 맥락 발견용이며 기존 ready 임베딩을 재사용한다. |
| interaction      | 한 만남의 일시·장소·행사·주제·요약. 참가자는 별도 연결하며 만남당 한 원본을 유지한다.  |
| memory_statement | 개별 사실·발언. 연결 인물과 만남, 사실 날짜 및 출처를 유지한다.                        |
| action_item      | 약속·후속 업무·저장된 제안. 종류·상태·기한·연결 만남을 유지한다.                       |

- 새 테이블은 interaction/memory_statement/action_item용이다. 각각 typed source FK를 두고 정확히 하나만 설정하도록 CHECK한다. `(workspace, kind, source_id, chunk_index, projection_version)` 유일성을 보장한다.
- 필드: content, content_hash, projection_version, occurred_at, due_at, kind/status, source 연결, embedding/model/status, lease token·만료, retry 정보. 참가자 연결은 workspace 복합 FK를 가진 `memory_search_unit_people`로 관리한다.
- provenance는 원본 레코드에 연결된 기존 `provenance_records`에서 읽는다. 실제 원문이 없는 과거 기록은 없다고 표시하고 만들지 않는다.
- 입력 단위가 길면 문단 경계로 결정론적으로 나누고 각 chunk를 같은 source에 연결한다. chunk는 새 사실이 아니다. v0.1 단위 상한은 4,000자 제안이며 임베딩 provider 입력 제한도 별도로 적용한다.
- 최신 확정·활성 원본만 projection에 포함한다. 내용 변경 시 기존 벡터는 즉시 무효화한다. archive, 참가자 제거, 약속 완료·기각 등도 검색 범위에 반영한다.
- 인물 archive가 만남 전체를 지우지 않게 한다. 다른 활성 참가자는 그 만남을 계속 검색할 수 있어야 한다.
- existing memory_documents를 제거하거나 기존 query_evidence를 깨지 않는다. 새 unit ID를 사실 근거 ID로 대신 쓰지 않고 원본 근거 키를 반환한다.

### 3.4 검색 및 맥락 구성

1. 질문 이해와 대상 확인을 먼저 수행한다. 검색 준비 확인으로 이 단계를 전역 차단하지 않는다.
2. workspace·활성 상태·확정 상태를 공통 조건으로 구조화 검색, 키워드 검색, ready 벡터 검색을 수행한다.
3. 이름/ID, 기한·상태·날짜 등 확정 조건은 구조화 경로로 확보한다. 한국어 키워드는 정규화 문자열 매칭을 기본으로 하고 기존 FTS는 보조 신호로 사용한다. 한국어 형태소 지원을 가정하지 않는다.
4. 각 경로 최대 24개, 중복 제거 후 최대 48개 후보를 RRF 방식으로 병합한다. 다른 척도의 점수를 그대로 더하지 않는다. 수치는 평가로 조정한다.
5. rerank 후 최대 12개 unit을 선택한다. 같은 원본의 chunk는 묶고 특정 인물의 기록이 전부를 차지하지 않게 제한한다.
6. 최신 원본과 필요한 주변 근거를 다시 읽는다. 맥락 확장은 동일 만남의 참가자·사실·할 일과 관련 인물의 직접 기록으로 제한한다. v0.1은 관계 hop 1, 전체 근거 최대 24개 제안이다.
7. 같은 만남 조건은 interaction ID로 검증한다. 기한 조건은 due_at, 만남 조건은 occurred_at로 검증한다. 후보 조건과 최종 근거 조건을 분리해 확인한다.

인물 관계 해석은 기존에 저장된 직접 참가·소속 관계까지만 사용한다. 암묵적인 친밀도·영향력 그래프를 추정하지 않는다.

### 3.5 부분 검색과 provider 장애

- coverage에는 `normal/limited/unavailable`, 사용한 경로, 의미 검색 준비 범위, 누락·절단 이유와 기준 시각을 담는다. `normal`도 세상의 모든 정보나 무한한 검색 재현율을 보장하지 않는다.
- ready 벡터가 없어도 최신 구조화·키워드 검색으로 답할 수 있다. 이 경우 의미 검색 범위 제한을 표시한다.
- 일부만 준비된 상태에서 근거가 없으면 “확인 가능한 범위에서 찾지 못함”으로 표현한다. 저장된 정보가 없다고 단정하지 않는다.
- 목록/우선순위 요청에서 후보 또는 근거 상한에 걸리면 제한을 알리고 기간·대상 축소를 제안한다.
- embedding 장애 시 구조화·키워드 경로, rerank 장애 시 병합 순위로 진행한다. 예약된 호출 예산 초과는 우회하지 않고 사용 가능한 경로만 활용한다.
- 질문 이해가 실패하면 구조화된 명시 입력으로 처리 가능한 제한된 조회만 제공하거나 다시 시도를 안내한다. 답변 모델 실패 시에는 근거 목록만 반환하고 생성 답변처럼 표시하지 않는다.
- 권한·DB 오류는 부분 검색으로 덮지 않는다. 사용자가 입력한 텍스트와 검색된 기록은 지시가 아닌 자료로 취급한다.

### 3.6 자동 인덱스 복구

DB 기반 `memory_index_jobs`와 bounded worker를 제안한다. 요청 종료 뒤 살아남는다고 가정한 메모리 timer나 fire-and-forget promise는 사용하지 않는다.

- 기록 저장 transaction 안에서 영향을 받는 검색 unit을 갱신·무효화하고 해당 hash/version의 job을 upsert한다. provider 호출은 transaction 밖에서 한다.
- Workspace mutation, text capture commit, business-card commit 모두 같은 projection 책임을 사용한다. 인물·만남·참가자·주제·할 일 변경의 영향 범위를 매핑한다.
- 대상·내용 hash·model 기준의 중복 작업을 합치고 claim은 row lock/lease token으로 보호한다. 예전 worker는 최신 내용의 ready/failed 상태를 덮어쓰지 못한다.
- 임베딩 성공은 현재 hash/version/token이 일치할 때만 반영한다. 변경됐다면 최신 job을 처리하고 과거 결과는 버린다.
- 재시도 제안: 재시도 가능한 네트워크/5xx/429만 최대 3회, 30초→2분→10분 지연, Retry-After 존중. 설정·입력 오류는 자동 반복하지 않는다.
- worker 실행은 최대 10 job 또는 20초 중 먼저 도달한 한도까지만 새 호출을 시작한다. 진행 중 호출은 provider timeout까지 끝날 수 있어 실행 플랫폼의 여유 시간도 확보한다. 비용 예약 한도에 닿으면 중단·보류한다.
- 로컬 개발은 전용 CLI worker를 별도 프로세스로 실행한다. 원격은 승인된 scheduler가 보호된 batch 실행 경로를 호출하도록 한다. 구체적인 scheduler 및 호출 간격은 운영 연결 때 결정한다.
- 자동 복구 활성화는 feature flag와 호출 한도로 제어한다. 검색 요청마다 임베딩을 생성하는 방식은 사용하지 않는다.
- 수동 복구도 같은 job 상태·예산을 사용한다. dead-letter/보류 사유와 마지막 처리 시각을 운영에서 확인한다.

“자동 복구 완료”는 worker 코드만 있는 상태가 아니다. 목표 실행환경에서 scheduler/worker가 실제 구동되고 재시도가 검증돼야 한다. 미연결이면 로컬 검증 완료와 원격 연결 미완료를 구분한다.

### 3.7 지연·호출 관리

- 기본 경로는 기존 네 호출 수준을 유지한다. 대화 참조 해석과 목적 선택을 질문 이해 호출에 합치고 별도 분류·요약 호출을 기본 추가하지 않는다.
- 확인 질문은 검색·답변 호출 전에 종료한다. 정형화된 인물/업무 목록은 필요한 provider 단계를 생략할 수 있다.
- 전체 요청 deadline 60초, UI timeout 70초를 초기 제안으로 두고 남은 시간 없이 다음 외부 단계를 시작하지 않는다.
- turn별 query understanding, 검색, rerank, 근거 구성, 생성, 검증, DB 저장의 시간과 provider 요청 횟수·토큰을 기록한다. 토큰만으로 금액이 확정된다고 보지 않는다.
- 단계 지표는 운영 기록에 저장하며 원문·개인 정보를 일반 로그에 노출하지 않는다. UI에는 자연스러운 작업 상태와 제한 사유를 표시한다.

## 4. 입력 파이프라인과 변경 경계

현재 추출·검토·commit 구조를 유지한다. 이번에는 사실과 맥락을 검색에서 활용할 수 있게 다음을 검증한다.

1. 인물, 만남/행사/장소, 주요 사실, action kind와 기한, 원문 출처가 원본에서 검색 근거까지 이어지는가.
2. 불확실한 인물·날짜가 사용자 확인 없이 확정 정보가 되지 않는가.
3. 단순히 언급한 장소와 실제 만남 장소, 만남 날짜와 행동 기한을 구분하는가.
4. 사용자가 수정한 사실과 종료한 약속, 제거한 참가자가 현재 답변에 반영되는가.

누락이 재현되면 해당 필드의 draft/검토/commit/근거 계약만 보완한다. 새 입력 채널이나 전체 OCR·STT 구조 변경은 포함하지 않는다. 생성된 해석과 추천은 별도 사용자 확정 절차 없이 canonical fact로 저장하지 않는다.

## 5. 구현 순서와 산출물

사용자 우선순위는 대화·안정성·맥락 검색이다. 기술 작업은 평가 기준을 먼저 만들고 각 단계를 독립 검토 가능하게 나눈다.

| 단계         | 구현 범위                                                                     | 단계 완료 기준                                                            |
| ------------ | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| P0 기준선    | 합성 fixture, 대표 사례, 기존 검색/지연 기준선, 작업 공간·DB 격리             | 기존 동작과 실패를 반복 측정하고 기준 commit·변경 소유권 기록             |
| P1 대화      | 세션/turn, 요청 멱등성, 참조 해석, 확인 UX, 복원·초기화                       | U1~U3/U9, 동명이인, 동시 turn·응답 유실·만료 테스트 통과                  |
| P2 안정성    | 전역 차단 제거, canonical fallback, coverage, 인물 인덱스 job·worker          | 일부/전체 벡터 미준비에도 가능한 경로 사용, 실패·중복·변경 중 재시도 검증 |
| P3 맥락 검색 | 새 unit projection, typed FK·참가자 연결, backfill, 하이브리드 검색·맥락 확장 | 여러 만남·수정·archive·한국어 키워드·행동 기한 구분, 검색 품질 gate 통과  |
| P4 가치 제공 | summarize/connect/prioritize/prepare, sections·근거 UX                        | U5~U8에서 실제 기록을 활용한 유용성 검토 및 unsupported claim 검사        |
| P5 통합 검증 | isolated live 평가, 기존 회귀, migration/flag 전환·worker 운영 검증           | 아래 전체 완료 기준 충족 및 결과 문서화                                   |

P1~P3만으로 제품 가치까지 완료했다고 보지 않는다. P4는 새 외부 행동 도구 도입 없이 개선된 맥락 기반을 사용자가 체감하도록 만드는 이번 범위다.

### 주요 코드 책임

- 신규 `src/domain/assistant/`: session/context, purpose/answer contract, claim validation.
- 신규 `src/server/application/assistant-service.ts`: turn orchestration. 검색·근거는 기존 Recall에서 공통 서비스로 추출.
- 신규 session/search unit/job repository와 worker service: DB 상태와 transaction 경계.
- 기존 `assistant.tsx`: 진입점 유지. 세션·근거·결과 section UI를 작은 컴포넌트로 분리.
- 기존 `live-recall-service.ts`, `assistant-contract.ts`, `memory-search-repository.ts`: 기존 API 호환 adapter와 공통 검색 책임으로 단계적 정리.
- 기존 workspace/capture/business-card 저장 지점: 새로운 projection·job 연결에 필요한 최소 변경.
- 신규 migration은 기존 migration을 고치지 않는다. 타입·제약·접근 정책, backfill과 feature flag를 함께 설계한다.

## 6. 완료 기준과 검증 기준

아래 수치는 **승인용 목표 제안**이며 달성 실적이 아니다. 모델 문장을 문자열 일치로 평가하지 않고 대상·조건·근거와 실제 유용성을 평가한다.

### 데이터셋 및 방법

- 합성 workspace 최소 15명, 40개 만남, 80개 사실, 30개 행동. 동명이인·공동 만남·날짜 미상·수정·archive·미준비 인덱스를 포함한다.
- 단일 turn 사례 최소 30개, 2~~5 turn 대화 최소 15개. lookup/summarize/connect/prioritize/prepare와 U1~~U10 모두 포함한다.
- 각 사례는 기준 시각, 상태, 대상/만남 ID, 필수·금지 근거, 허용 해석, 금지 주장, coverage 기대를 기록한다.
- 검색 평가는 answer LLM을 분리하고, 생성 평가는 고정 근거와 end-to-end를 각각 사용한다. mock 통과를 live 품질 증거로 대체하지 않는다.
- live 대화 평가를 고정 설정으로 3회 반복해 변동성을 기록한다. 독립된 holdout 사례를 포함하고 조정용 사례와 구분한다.

| 영역      | 완료 및 통과 기준                                                                                                                                                                          |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 기능·회귀 | 기존 단일 질문·근거·피드백·기록 저장·화면 연결 회귀 100% 통과. 새 세션 복원·초기화 및 U1~U10의 상태 처리 통과                                                                              |
| 참조 해석 | holdout에서 올바른 대상 유지/확인 질문 비율 95% 이상. 동명이인·다중 후보를 무단 확정하는 중요 실패 0건                                                                                     |
| 검색      | 평가 질문별 필수 원본 근거 recall@12 평균 90% 이상, 기존 확정 중요 사례는 누락 0건. 관련 없는 근거를 상위에 넣는 precision도 함께 보고                                                     |
| 근거·경계 | 다른 workspace/삭제·archive·미확정 근거 노출 0건. 존재하지 않는 근거 키·같은 만남 오결합·약속/제안 혼동·기한/만남 날짜 혼동 0건                                                            |
| 유용성    | 정리·연결·판단·준비 사례의 최소 90%가 목적 충족, 관련성, 다음 행동의 구체성 각 4/5 이상. 중요한 근거 없는 사실 주장 0건. 사람이 검토                                                       |
| 복구      | 일부·전체 벡터 미준비, 429, provider outage, 동시 claim, worker 중단, 기록 변경 중 embedding 완료를 강제해 상태 전이·제한 안내가 기대와 일치                                               |
| 갱신      | 저장 직후 canonical/키워드 경로에서 변경을 조회 가능. 건강한 worker가 10초 간격으로 실행되고 예산이 허용되는 10 job 이하 fixture에서 60초 안에 ready 도달. 그 조건 밖은 지연을 숨기지 않음 |
| 멱등성    | 동일 요청 재전송에서 완료된 호출·turn 중복 생성 0건. 처리 중 재전송은 상태 반환. lease 만료의 불명 결과는 자동 billable 재실행하지 않음                                                    |
| 지연·비용 | 고정 환경·데이터의 비교 사례 최소 30개에서 기본 조회 p95가 기준선 대비 10% 넘게 악화되지 않고, 성공 응답이 60초 deadline 안에서 끝남. 확장 답변은 별도 p50/p95·호출 수 보고                |
| 운영      | 자동 재시도 횟수·예산 한도·dead-letter·수동 재개 검증. 실제 대상 환경의 worker/scheduler 연결 여부 명시                                                                                    |

생성 품질 점수는 초기에 개발자 검토하고 최종 제품 경험은 사용자가 검토한다. 평균 점수가 높아도 데이터 경계 및 중요 사실 오류가 있으면 완료로 판정하지 않는다.

### 자동화 검증

- domain/unit: 참조 우선순위, 날짜 조건, 범위 상속, 상태와 근거 계약.
- DB integration: composite FK/접근 범위, session 예약·멱등성, job lease/hash, source 갱신·archive 및 공유 만남 처리.
- API: 과거 Recall 호환, 세션 소속, 입력 제한, 409·처리 상태·부분 검색 오류.
- E2E: `/`의 `/#todos`에서 후속 대화, 후보 선택, 새로고침, 새 대화, 사실/해석/제안·근거, 검색 제한 안내.
- isolated live: 의미 참조, 한국어 검색, 목적별 결과, provider 실패와 호출 계측.
- 단계 완료 시 lint/typecheck/unit/build, 최종 `npm run verify` 및 관련 E2E 실행. 원격 DB 검증과 live 호출은 승인된 대상·예산으로 수행한다.

이번 문서 작성 중에는 위 테스트, live 호출, benchmark를 실행하지 않았다.

## 7. 데이터 전환·병렬 작업·복구

- [인계 문서](../handoff/ai-assistant-direction-2026-10-13.md)의 전용 worktree/브랜치 제안을 유지한다. 현재 다른 작업의 미커밋 변경은 작업 기준에서 자동 포함되지 않는다.
- 기준 commit과 포함할 최신 UI 변경을 합의한 다음 worktree를 만든다. 공유 폴더에서 브랜치 전환·다른 변경 commit/stash를 하지 않는다.
- 우선 AI domain/service/repository/테스트를 별도 파일로 만든다. `assistant.tsx`, workspace/capture repository, 공통 타입·env·migration은 다른 세션과 변경 책임을 조율한다.
- 독립 DB/브랜치와 전용 workspace·서버 포트·빌드 출력으로 검증한다. 같은 DB의 migration은 workspace ID만으로 격리되지 않는다.
- additive schema → 새 projection backfill → 비교 평가 → 새 UI/API·검색 flag 활성화 순서로 전환한다. backfill은 제한된 배치와 재개 지점을 제공한다.
- 기존 canonical 데이터·과거 질문 근거를 삭제하지 않는다. 문제 시 flag로 기존 Recall 경로를 유지하고 worker를 멈춘다. 신규 테이블을 급히 삭제하는 방식으로 롤백하지 않는다.
- 상세 schema SQL, scheduler 선택, 환경 변수 이름, migration 번호는 실제 구현 기준 commit에서 확정한다.

## 8. 승인 전 검토할 핵심

1. 이번 범위에 상황 정리·연결·우선순위·준비 초안까지 포함하되, 저장·외부 실행은 후속으로 두는가.
2. 서버 저장형 세션과 현재 프로토타입 접근 경계, 보존 기간 제안을 수용하는가.
3. 별도 검색 unit 테이블과 제한된 자동 복구 worker를 수용하는가.
4. 테스트·live 평가 예산과 대상 환경을 정하고 기준 commit·공통 파일 변경 책임을 합의할 수 있는가.

이 항목은 설계 검토 지점이다. 아직 승인된 결정이나 실행 완료로 기록하지 않는다.
