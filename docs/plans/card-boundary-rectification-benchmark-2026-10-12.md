# 단일 명함 외곽 인식과 복원 정량 검증 기준

- 기준일: 2026-10-12
- 상태: 구현 전 검증 설계. 수치는 통과 기준 또는 최적화 목표이며 측정 결과가 아니다.
- 적용: [작업 설계](card-boundary-rectification-design-2026-10-12.md)의 1~6단계. 본 문서가 세부 평가 정의와 판정의 기준이다.
- 원칙: 내용 보존과 정확성을 먼저 판정하고 속도·안정성을 각각 판정한다. 한 항목의 높은 점수로 다른 항목의 실패를 상쇄하지 않는다.

## 1 통과 판정과 기준 변경

| 분류           | 판정                                                                                         |
| -------------- | -------------------------------------------------------------------------------------------- |
| 필수 품질 기준 | 모두 충족해야 품질 PASS. 내용 잘림·잘못된 소스 연결 등 중대 오류 한 건이면 FAIL              |
| 필수 성능 기준 | 명시한 기준 기기·입력·네트워크에서 충족해야 성능 PASS. 품질 기준을 완화해 속도를 맞추지 않음 |
| 최적화 목표    | 미달해도 필수 기준 PASS 가능. 달성 여부와 기준까지 남은 차이를 함께 보고                     |
| 미측정         | NOT_RUN. 실기기·정답·측정 도구 등이 없어 필요한 지표가 없으면 통과로 간주하지 않음           |
| 표본 부족      | INSUFFICIENT_DATA. 파일럿 통과와 최종 검증을 분리                                            |

도구별 보조 측정에는 NOT_SUPPORTED도 사용한다. 이는 해당 API의 미지원 상태이며 0이나 PASS로 바꾸지 않는다. long task·JS heap 같은 보조 API가 미지원이면 명시한 대체 필수 시험을 적용하고, 대체 시험도 없으면 해당 필수 항목은 NOT_RUN이다.

품질·성능·안정성·데이터 충족 여부를 별도 열로 표시한다. 제품 기본 경로 전환은 필요한 최종 기준을 모두 충족한 뒤 판단한다. 다음 단계의 기술 작업은 병행할 수 있지만 이전 단계 FAIL을 완료로 기록하지 않는다.

기준·데이터 분할·모델·runtime·정밀화 threshold는 보류 평가 전에 버전과 해시를 고정한다. 보류 결과를 보고 수정하면 그 데이터는 튜닝 자료로 편입하고 새로운 보류 자료로 다시 검증한다. 어려운 입력이나 느린 실행을 결과에서 지우지 않는다. 기준 변경 시 이유·이전 결과·변경 영향을 기록한다.

3초는 기존 합의대로 **촬영 확정에서 필드 수정 가능까지의 지향 목표**다. 아래 4초 등의 복원 연산 기준은 별도 구간의 신규 설계값이며 3초를 필수 기준으로 바꾸는 뜻이 아니다. 절대 성능 기준은 첫 실기기 실행 전의 개발 판정값이다. 장치별 미달은 미달로 기록하고 제품 대상 기기·실행 경로를 검토한다.

## 2 데이터와 정답의 준비 기준

### 평가 집합

| 집합                | 최소 구성                                      | 사용과 판정                                                                                             |
| ------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 합성 정상 명함      | 60개 도안 × 20개 촬영 변환 = 1,200장           | 개발 36도안·720장, 튜닝 12도안·240장, 보류 12도안·240장. 같은 도안은 한 분할에만 배치                   |
| 합성 명함 없음      | 300개 배경 장면                                | 모니터·책상·노트·프레임 등 유사 사각형 포함. 합성 회귀에 사용하며 실사진 오검출 확률의 근거로 쓰지 않음 |
| 합성 비정상 입력    | 200장                                          | 교차 코너·프레임 밖 코너·잘린 이미지·불충분한 해상도·잘못된 형식 등 처리와 실패 판정                    |
| 실제 사진 파일럿    | 현재 예정 약 20장                              | 물리적 카드로 분리하여 약 10장 튜닝·10장 보류. 실제 카드 수와 분할 후 사진 수 기록                      |
| 실제 최종 정상 명함 | 보류 자료에 서로 다른 카드 ≥100개, 사진 ≥300장 | 기기·배경·각도 다양화. 튜닝 카드와 중복 금지. 실제 품질 최종 판정                                       |
| 실제 명함 없음      | 독립 장면 ≥300장                               | 정상 복원 후보의 오검출 최종 판정. 같은 사진 변형은 독립 장면 수에 합산하지 않음                        |
| 실제 재촬영 대상    | ≥50장                                          | 가림·프레임 밖·심한 흐림·정보 소실. 정상 복원으로 잘못 처리하는지 검수                                  |

현재 사진 경로는 제공될 때까지 보류한다. 합성 정상·비정상, 공식 모델 재현, 기술 호환성 검증은 먼저 진행할 수 있다. 최종 표본을 현재 확보했다고 보고하지 않는다.

합성 명함 없음 300개와 비정상 200개는 보류 시험용으로 고정한다. threshold 조정을 위한 부정·비정상 예시는 별도 seed·배경으로 추가하며 보류 입력을 재사용하지 않는다. 실제 명함 없음 300장·재촬영 50장도 보류 자료이며 튜닝용 자료와 독립적으로 수집한다.

조건 태그는 작은 명함, 화면을 거의 채운 명함, 흰 배경의 흰 명함, 어두운 명함, 복잡한 배경, 강한 원근, 90도 이상 회전, 둥근 모서리, 그림자, 반사, 흐림, 정면 스캔을 사용한다. 최종 정상 집합에서 해당되는 주요 조건별 ≥20장을 목표로 하고 태그는 중복 가능하다. 조건별 표본이 부족하면 해당 조건은 INSUFFICIENT_DATA로 남긴다. 가림이나 정보 소실은 정상 집합과 분리하되 전체 결과에서 누락하지 않는다.

### 정답과 라벨 품질

정답 manifest에 imageId·cardId·split·조건 태그·파일 SHA-256·방향 적용 후 크기·코너·실제 비율·필수 내용 영역·재촬영 사유를 기록한다. 합성은 도안과 적용 변환의 수학적 정답을 사용한다. 실제 정상 명함은 보류 평가 전에 두 번 독립적으로 코너를 확인하고 이견을 해결한다.

- 네 변이 직선인 명함은 변의 교점을 라벨링한다. 둥근 코너도 같은 정의를 사용한다.
- 두 라벨의 평균 차이 ≤명함 대각선의 0.15%, 최대 차이 ≤0.5%를 준비 기준으로 둔다. 초과하면 재검수한다.
- 완전한 외곽이 보이지 않거나 정답을 확정할 수 없는 사진은 평가 전에 재촬영·불확실 집합으로 지정한다. 모델 결과를 본 뒤 정상 사진을 제거하지 않는다.
- 이름·전화·이메일·로고 등 반드시 보존할 인쇄 영역을 polygon으로 표시한다. 합성은 글자·로고별 마스크도 제공한다.
- 실제 비율 오차 평가는 실측 가로·세로가 있는 사진 ≥50장·서로 다른 카드 ≥30개가 있어야 최종 판정한다. 자동 근사·사용자 규격 입력·보정 정보 경로를 각각 집계한다.
- 파일·라벨·실제 결과는 Git 제외 로컬 평가 디렉터리에 보관한다. 공개 가능한 합성 fixture만 저장소에 넣는다.

## 3 지표의 계산과 집계

방향을 적용한 이미지 좌표에서 정답 코너를 `g_i`, 예측 코너를 `p_i`라 한다. 정규화 기준 길이는 `D = max(distance(g_0,g_2), distance(g_1,g_3))`이다. 시작점 차이는 시계방향 순서의 순환 이동으로 맞추되, 뒤집힌 순서나 자기 교차는 유효 예측으로 처리하지 않는다.

| 지표                      | 계산 또는 정의                                                                         |
| ------------------------- | -------------------------------------------------------------------------------------- |
| 카드 평균 코너 오차 Emean | `100 × mean_i(distance(p_i,g_i)) / D`, 단위 %                                          |
| 카드 최대 코너 오차 Emax  | `100 × max_i(distance(p_i,g_i)) / D`, 단위 %                                           |
| 외곽 IoU                  | 예측 polygon과 정답 polygon의 교집합 면적 / 합집합 면적                                |
| 외곽 검출 성공            | 유효한 네 점, IoU ≥0.985, Emax ≤1.5%를 모두 충족한 정상 입력                           |
| 안전한 후보 제시율        | 품질 기준을 충족한 정상 복원 후보 수 / 전체 정상 입력 수                               |
| 잘못된 정상 후보율        | 기준 미달인데 정상 후보로 제시한 수 / 전체 입력 수. 사진 집합별 분리                   |
| 내용 보존율               | 필수 영역 M마다 `area(M ∩ 예측영역) / area(M)`. 한 영역이라도 99.9% 미만이면 잘림 판정 |
| 비율 오차                 | `100 × abs(출력비율 / 실제비율 - 1)`; 90도 회전 시 실제비율도 대응하여 비교            |
| 수정 없는 채택률          | 최초 후보를 코너·비율 수정 없이 채택하고 내용 보존 검수도 통과한 사진 / 전체 정상 사진 |
| 복원 손상                 | 정답 코너와 실제 비율로 같은 촬영 소스를 변환한 기준 이미지와의 SSIM·PSNR·색 차이      |
| 작업 오류율               | 취소 의도가 없는 요청에서 오류·시간 초과·탭 종료·결과 없음이 발생한 수 / 요청 수       |

SSIM은 영상 구조 유사도, PSNR은 픽셀 오차를 신호 크기와 비교한 값, ΔE00은 색 차이다. 복원 지표의 기준 이미지는 동일 촬영 소스를 사용하므로 조명 변화와 알고리즘 손상을 혼동하지 않는다. 실제 정면 스캔과의 색·SSIM은 조명·색 보정 조건이 맞지 않으면 참고 수치로만 기록한다.

코너 오차 분포에는 네 점이 유한하고 대응 가능한 모든 예측을 넣는다. 후보로 거절된 예측도 포함하며 잘 나온 사진만 선택하지 않는다. 네 점 미검출·비정상 좌표는 오차 분포에 가짜 값을 넣지 않고 별도 실패 수로 표시하고 성공률 분모에는 포함한다. 평균 IoU 집계에서는 미검출·비정상 예측을 0으로 처리한다. 조건별 성공률과 오차를 전체 수치 옆에 반드시 표시한다.

### 영상 지표의 고정 계산 방식

벤치마크 수집은 Node·Playwright, 영상 수치 계산은 평가용 Python의 NumPy·scikit-image를 재사용한다. 이는 개발 평가 도구이며 웹 제품의 런타임 의존성을 늘리는 설정이 아니다. 평가 도구 버전과 요구사항 파일도 실행 결과에 고정한다.

| 항목           | 고정 설정                                                                                                                                            |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 색과 크기      | 기준·결과를 같은 sRGB 8-bit RGB, 동일 width·height로 비교. 크기 불일치를 임의 resize로 숨기지 않음                                                   |
| SSIM           | structural_similarity, data_range=255, channel_axis=-1, gaussian_weights=True, sigma=1.5, win_size=11, use_sample_covariance=False, K1=0.01, K2=0.03 |
| 인쇄 영역 SSIM | 정답의 글줄·로고 ROI 사용. 최소 11×11을 확보할 주변 영역을 평가 전에 지정, 이미지별 유리한 ROI 재선택 금지                                           |
| PSNR           | RGB 세 채널 전체 MSE로 10×log10(255²/MSE). MSE=0이면 +Inf로 기록하고 정상 일치로 판정                                                                |
| ΔE00           | sRGB→Lab, illuminant=D65·observer=2, deltaE_ciede2000의 kL=kC=kH=1. 사전 지정 평탄한 색 ROI의 경계 2px를 제외한 픽셀에서 집계                        |
| 출력 비교      | 같은 JPEG를 같은 decoder로 읽어 기준·결과 비교. decoder와 ICC 처리도 기록                                                                            |

지표 구현은 동일 이미지의 SSIM=1·PSNR=+Inf·IoU=1, 알려진 평행 이동의 코너 오차, 단색 픽셀 오차의 PSNR 등 독립적인 계산 정답으로 검증한다. metric 구현 오류가 있으면 모델 gate 이전의 평가 준비 단계가 FAIL이다.

## 4 외곽 인식 필수 품질 기준

같은 코드와 threshold로 합성 보류·실제 보류를 각각 평가한다. 표본이 충족된 집합에 대해 다음을 모두 판정한다.

| 지표                           | 통과 기준                                                     |
| ------------------------------ | ------------------------------------------------------------- |
| 평균 Emean                     | **≤0.35%**                                                    |
| Emean p95                      | **≤0.75%**                                                    |
| Emax p95 / 전체 최대           | **≤1.0% / ≤1.5%**                                             |
| IoU 중앙값 / p5                | **≥0.995 / ≥0.985**                                           |
| 외곽 검출 성공률               | 정상 집합 **≥95%**, 표본이 충분한 어려운 조건별 **≥90%**      |
| 필수 내용 잘림                 | 정상 후보에서 **0건**, 영역별 보존율 ≥99.9%                   |
| 잘못된 정상 후보               | 최종 실제 정상 집합 **0건**. 불확실한 결과는 검토 경로로 제시 |
| 명함 없는 사진의 정상 후보     | 실제 독립 장면 **0/300건**                                    |
| 재촬영 대상의 잘못된 정상 후보 | **0/50건**, 검토·재촬영 안내 비율 100%                        |
| 수정 없는 채택률               | 최종 정상 집합 **≥95%**, 어려운 조건별 ≥90%                   |

오차·IoU만 통과해도 글자·로고가 잘리면 FAIL이다. 후보를 거의 제시하지 않아 잘림 0건을 만드는 경우는 제시율·채택률 기준에서 탈락한다. 정상 후보라는 이름으로 반사나 가림으로 사라진 내용을 복구했다고 제시하지 않는다.

파일럿은 보류 사진 수 n에 대해 성공·채택 수가 `ceil(0.95 × n)` 이상인지 보고한다. n=10이면 10/10이 필요하다. 파일럿 성공을 최종 실제 검증 PASS로 옮기지 않는다.

후보 모델들은 일반 문서 코너를 예측하므로 높은 코너 score가 명함의 존재를 입증하지 않는다. 책·모니터·종이 문서의 오검출 기준에 미달하면 기본 채택을 보류한다. 필요하면 명함 유무 판단 또는 부정 예시 추가 학습을 별도 작업으로 설계하고 같은 보류 기준으로 다시 평가한다.

### 경계 정밀화의 별도 채택 기준

같은 입력·검출 모델에서 정밀화 전후를 비교한다. 기존 평균 오차가 0.15%를 초과하는 경우 평균 Emean 상대 감소 ≥15%, Emax p95 증가 ≤0.05%p, IoU p5 감소 ≤0.002, 새 내용 잘림 0건을 채택 기준으로 둔다. 정밀화 p95 시간은 400ms 이하여야 한다.

이미 평균 오차 ≤0.15%인 경우 상대 개선율을 강제하지 않고 동일한 비열화 기준을 적용한다. 기준 미달이면 정밀화를 기본으로 끄고, 모델만으로 전체 품질 기준을 충족하는지 판정한다. 모델 score의 threshold와 위치 보정은 튜닝 자료에서만 결정한다.

## 5 평면 복원 필수 품질 기준

검출기 오차와 복원기 오차를 분리하기 위해 정답 코너를 입력하는 시험과 실제 모델 코너를 사용하는 시험을 나눈다.

| 시험                            | 통과 기준                                                                                                                          |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 좌표 변환                       | 원본↔normalized↔모델↔ROI 왕복 오차 **≤0.25 원본 px**, 1,000개 유효 합성 기하 사례 전부 통과                                        |
| 방향과 순서                     | EXIF 1~8, 0·90·180·270도, 가로·세로 입력의 방향·점 대응·출력 크기 시험 **100% 통과**                                               |
| 잘못된 기하                     | 교차·중복·오목·프레임 밖·불안정 변환·비유한 좌표를 포함한 200개 사례 **100% 거부 또는 검토 처리**                                  |
| 규격 입력 복원                  | 정답 코너·실제 규격 사용 시 비율 상대 오차 **≤0.5%**. 픽셀 정수화 오차도 포함하며 반올림 원인이라는 이유로 초과 값을 제외하지 않음 |
| 자동 비율 경로                  | 실제 규격이 알려진 사진에서 오차 **중앙값 ≤1%, p95 ≤2%, 최대 ≤3%**                                                                 |
| 근사 미리보기                   | `estimated` 출처 기록 **100%**, 비율 조정 가능 **100%**, 근사를 실측 비율로 저장하는 사례 **0건**                                  |
| 필수 인쇄 내용                  | 원본의 필수 영역 보존 ≥99.9%, 잘림·순서 변경·가짜 문자 **0건**                                                                     |

| 정답 코너 복원의 글자·로고 영역 | 기준 이미지 대비 SSIM **≥0.980**, 모든 필수 영역 통과                                                                              |
| 평탄한 색 영역                  | 기준 이미지 대비 ΔE00 **중앙값 ≤1, p95 ≤3**, 사전 지정한 색 영역에서 측정                                                          |
| 출력 계약                       | 긴 변 ≤2600px·총 ≤4MP·JPEG ≤3,200,000 bytes·유효 차원 **100% 만족**                                                                |

영상 기준 이미지는 공식 OpenCV 기준 변환, 고정 보간법·색 경로·출력 크기로 생성하고 해시를 고정한다. 실제 모델 코너 결과에 자유로운 재정렬 homography를 다시 맞춰 오류를 지우지 않는다. 픽셀 비교의 허용 정렬은 사전에 정한 최대 1px의 평행 이동뿐이며 적용량도 기록한다.

단순 근사 비율이 자동 비율 기준에 미달하면 자동 비율 품질 FAIL이다. 규격 입력 경로의 성공으로 이를 덮지 않는다. 외곽 감지 기능은 별도 통과할 수 있고 비율 확인이 필요한 경로로 제공할 수 있지만, 전자동 원본 비율 복원 통과로 보고하지 않는다.

| ------------------ | ------------------------------------------------------------------------------------------------------------------------------- |

FP16·INT8은 위 FP32 수치 허용값을 임의로 늘려 통과시키지 않고 별도 후보로 평가한다. 양자화 채택 조건은 전체 품질 기준 충족, FP32 대비 채택률 하락 ≤0.5%p·Emean p95 증가 ≤0.05%p·IoU p5 감소 ≤0.002·새 잘림 0건이다. 전체 반복 처리 p95 ≥15% 단축 또는 실제 전체 전송 바이트 ≥20% 감소가 없으면 기본 적용하지 않는다.

## 7 속도 벤치마크 조건과 반복 수

### 기준 기기와 실행 조건

개발 시작 시 실제 확보한 중급 Android 1대, iPhone 1대, 개발 PC를 기준 기기로 고정한다. Android는 RAM 6~8GB급을 시작 대상으로 삼되 모델명·SoC·RAM·OS·Chrome 버전을 기록한다. iPhone도 모델·OS·Safari 버전을 기록한다. RAM만으로 성능이 동일하다고 간주하지 않는다. 모바일 viewport 결과는 PC 결과로 기록한다.

- Next production build와 실제 모델로 측정한다. dev 컴파일·개발 overlay·콘솔 대량 출력은 성능 측정에서 제외한다.
- 입력은 기준 파일 20장으로 고정하며 2·8·12MP, 긴 변·coverage·조건 태그를 기록한다. 파일 크기는 현재 10MiB 제한 이내다. 각 후보는 같은 파일을 사용한다.
- 로컬 연산 벤치마크는 네트워크·DB·OCR을 포함하지 않는다. 실제 UI·저장·OCR 시간은 별도 실행으로 측정한다.
- 네트워크 포함 시험은 내려받기 **10Mbps**, 업로드 **5Mbps**, RTT **80ms**, 인위적 손실 0%를 기준으로 둔다. shaping 구현과 실제 측정값을 기록한다.
- 앱은 전경 상태, 화면 자동 잠금 해제, 저전력 모드 해제, 같은 화면 밝기 조건을 유지한다. 배터리·충전·발열 상태를 기록한다.
- 후보 순서는 세션마다 교차 배치한다. 열로 느려진 결과도 별도 표시하며 빠른 실행만 추려내지 않는다. 전경 유지 실패 등 실행 조건 위반은 사유와 원자료를 남기고 다시 측정한다.

반복 200회는 최소 4개 세션으로 나누고 세션 ID를 기록한다. 각 후보가 같은 파일·반복 수를 처리하게 하며 초기 5회 준비 실행은 세션마다 원자료에 남긴다. Worker 내부 구간은 해당 Worker의 시작·끝으로 계산하고 전체 시간은 호출한 화면의 한 clock에서 측정한다. 다른 realm의 performance.now 값을 직접 빼지 않는다. WebGPU는 출력이 CPU에서 사용 가능한 시점까지 대기하여 실제 완료·전송 시간을 포함한다.

### 캐시 상태와 샘플 수

| 구간          | 정의                                                  | 반복 수                                                                  |
| ------------- | ----------------------------------------------------- | ------------------------------------------------------------------------ |
| 최초 다운로드 | 브라우저 모델·runtime cache 비움, Worker·session 없음 | 후보·기기별 **50회**, p50·p95·최대 보고                                  |
| 캐시된 재진입 | 파일 cache 존재, 새 Worker·session, 새 이미지 decode  | 후보·기기별 **50회**, p50·p95·최대 보고                                  |
| 반복 처리     | 동일 Worker·session, 새 입력 decode부터 JPEG 완료까지 | 후보·기기별 준비 5회 후 **20파일 × 10회 = 200회**, p50·p95·p99·최대 보고 |
| 누적 사용     | 주 모델로 처리→결과 해제, 취소·재촬영 포함            | 기기별 **100회 연속**, 오류·자원 잔류·메모리 추이 보고                   |
| 실제 저장     | 통제 네트워크와 실제 DB·Storage, 합성 명함            | 기준 환경 **50회**, 파일·요청 바이트·응답 시간·정리 결과 보고            |

30회 이하 실행은 예비 측정으로만 표시한다. 준비 5회는 반복 집계에서 제외하되 원자료에 남긴다. 그 이후 느린 값은 제외하지 않는다. percentile은 정렬한 n개 값의 `ceil(q×n)`번째 값으로 계산하고 ms 단위를 사용한다. 50회 최초 실행에서는 p99 대신 최대값을 보고한다.

오류·시간 초과는 별도 비율로 집계하고 완료 시간의 p95에서 조용히 제거하지 않는다. 완료된 실행의 분포와 전체 요청 오류율을 함께 보고하며 필수 성능 판정에는 오류율 0%를 요구한다. 반복 전체 시간의 p95 기준은 200회 합계와 각 세션 모두에 적용한다.

정상 성능 시험의 fallback·JPEG 미생성·엔진 오류는 실패로 센다. 재촬영·검토가 정답인 입력의 정상 처리 시간은 별도 집합에서 측정한다. 품질 판정이 필요한 데이터를 즉시 fallback해 속도 수치만 통과시키지 않는다.

## 8 속도와 사용자 응답성 기준

아래 필수 기준은 고정 기준 기기의 각 결과에 적용한다. PC·Android·iPhone 결과를 섞은 평균으로 통과시키지 않는다. 구간별 p95 합은 전체 p95가 아니므로 전체 경로도 직접 측정한다.

| 측정 구간                       | 필수 통과 기준                                                               | 최적화 목표  |
| ------------------------------- | ---------------------------------------------------------------------------- | ------------ |
| 반복 decode                     | p95 ≤350ms                                                                   | ≤200ms       |
| 모델 전처리·좌표 복원           | p95 ≤100ms                                                                   | ≤60ms        |
| 모델 추론                       | p95 ≤1,200ms                                                                 | ≤600ms       |
| 경계 정밀화·후보 검증           | p95 ≤400ms                                                                   | ≤200ms       |
| 원근 변환                       | p95 ≤650ms                                                                   | ≤350ms       |
| JPEG 인코딩                     | p95 ≤450ms                                                                   | ≤250ms       |
| 반복 전체 로컬 복원             | **p95 ≤4,000ms, p99 ≤6,000ms**, 오류·15초 초과 0/200                         | p95 ≤2,500ms |
| 캐시된 새 session부터 후보 준비 | p95 ≤6,000ms                                                                 | ≤4,000ms     |
| 최초 다운로드부터 후보 준비     | 통제 네트워크 p95 ≤20,000ms, timeout 0/50                                    | ≤12,000ms    |
| 준비된 후보의 OK 이후 표시      | OK 응답 수신→후보 화면 갱신 p95 ≤150ms                                       | ≤80ms        |
| 처리 시작 피드백                | 사용자 동작→진행 상태 표시 p95 ≤100ms                                        | ≤50ms        |
| 취소 피드백                     | 취소 동작→화면 처리 중단 p95 ≤100ms, 늦은 결과 적용 0건                      | ≤50ms        |
| 전체 복원 자산 전송             | 최초 모델·runtime의 실제 전송량 ≤30MiB. cache 재진입 불필요한 재다운로드 0건 | ≤20MiB       |
| 채택→소스·표시 저장 완료        | 통제 네트워크·실제 저장 p95 ≤12,000ms, 실패 0/50                             | ≤6,000ms     |

현재 20초는 런타임 준비의 제한값이며 최초 실행 전체의 p95 20초 기준과 구분한다. 준비 단계가 20초를 넘거나 이미지 작업이 15초를 넘으면 중단·실패로 집계한다. timeout이 있는 실행을 완료값만으로 통과시키지 않는다. 준비는 제한 안에 끝났지만 전체 최초 실행이 느린 경우도 전체 시간 분포에 포함한다. 대용량 최초 다운로드가 기준을 넘으면 자산·캐시·준비 시점을 개선하고 최초 결과를 별도로 보고한다.

### UI와 기존 OCR에 미치는 영향

| 지표                  | 필수 기준                                                                                                         |
| --------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 처리 중 입력 응답     | ≥200개 입력 이벤트의 handler 시작→다음 화면 반영 p95 ≤100ms, p99 ≤200ms. 지원 시 실제 event 시작→반영도 별도 기록 |
| 화면 프레임 간격      | 전경 60Hz 기준 rAF 간격 p95 ≤50ms, 200ms 초과 **0건**. 화면 주사율과 측정 가능 여부 기록                          |
| 메인 스레드 long task | 지원 브라우저에서 복원 구간의 200ms 이상 task **0건**, `sum(max(0,duration-50ms))` p95 ≤100ms/작업                |
| OCR 병행의 회귀       | 고정 1·3·5초 mock OCR 조건 각각에서 필드 수정 가능 p95 증가 **≤10%이면서 ≤150ms**, 오류 증가 0건                  |
| 확정 정보와 관계 저장 | 복원 전후 필드 변경 **0건**, OK만으로 인물·만남·그래프 생성 **0건**, OK 전 후보 공개 **0건**                      |

Long Tasks API가 지원되지 않으면 long task 값은 N/A로 남기고 rAF·입력 화면 반영 기준을 적용한다. N/A를 long task 0으로 쓰지 않는다. handler 이후 측정은 입력 queue 대기를 포함하지 않으므로 실제 입력 지연이나 INP로 이름 붙이지 않는다. 브라우저별로 수집 가능한 실제 event timing과 차이를 기록한다.

live OCR의 실제 `촬영→필드 수정 가능`은 provider·업로드·서버 시간을 포함해 별도 관측한다. p95 3초 달성 여부를 기록하되 mock의 속도를 live 처리 성능으로 표시하지 않는다. 외곽 벤치마크 자체는 유료 AI를 호출하지 않는다.

## 9 메모리와 저장 안정성 기준

| 항목                    | 필수 기준과 시험                                                                                                                    |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 관리하는 픽셀 작업 버퍼 | 동시에 보유하는 크기를 합산하여 **최대 128MiB**, ROI Mat ≤8MP. 모델 heap·브라우저 내부 decode·GPU와 구분                            |
| 객체 해제               | 작업별 Mat·ImageBitmap·tensor·Object URL의 생성/해제 추적. 종료 후 미소유 객체 **0개**. 현재 표시 이미지와 공유 session은 따로 계수 |

| 저장 소스 재복원        | 첫 결과 대비 SSIM ≥0.985, 글자·로고 영역 ≥0.975, 비율 변화 ≤0.2%, 추가 잘림 **0건**                                                 |

| 중복 저장               | 동일 멱등성 요청 100회 재전송에서 중복 최종 자산·revision 증가 **0건**                                                              |
| 동시 저장 충돌          | 서로 다른 요청 100쌍에서 이전 revision을 덮는 갱신 **0건**. 같은 요청은 동일 결과, 다른 요청은 한 갱신만 성공                       |
| 장애 복구               | 소스·표시 업로드·DB transaction·후속 정리 실패 주입을 단계별 20회 수행. 기존 유효 결과 손실 **0건**                                 |
| 삭제와 임시 자산        | 시험 종료 후 잔여 참조·대상 파일 **0개**. 24시간 만료 작업으로 정리해야 할 임시 파일 100% 식별                                      |

JS heap 측정 미지원 시 객체 계수·버퍼 합계·100회 실제 사용을 필수로 유지하고 heap 수치는 NOT_SUPPORTED로 표시한다. 지원 API가 있지만 실제 수집하지 않았다면 NOT_RUN이다. 전체 프로세스 peak RSS는 OS 도구가 있으면 함께 기록하며 측정하지 못한 메모리까지 128MiB 이하라고 주장하지 않는다. forced GC는 누수 진단에만 사용하고 속도 벤치마크에는 넣지 않는다.

개인 원본 삭제 후 복원 소스가 남거나, DB 실패 후 기존 정상 결과가 사라지는 경우는 성능 수치와 관계없이 안정성 FAIL이다. 과거 v1 데이터·nullable 소스·기존 입력 API 호환 시험도 전부 통과해야 한다.

## 11 통계와 후보 비교

성공률·채택률·오검출율은 분자/분모를 함께 표시한다. 실제 사진은 카드별 반복이 있으므로 사진 단위 point estimate와 카드별 결과를 함께 제공하고, 차이의 95% 구간은 카드 단위 paired bootstrap 5,000회로 계산한다. 합성 변형이나 같은 카드의 반복 사진을 새로운 독립 카드로 세지 않는다.

시간은 기기별 percentile과 세션별 percentile을 함께 표시한다. 후보 간 시간 차이의 95% 구간은 같은 입력 파일·세션을 대응시킨 block bootstrap 5,000회로 계산하고 세부 seed·block 구성도 기록한다. 특정 20개 입력의 200회 실행은 그 조건의 반복 성능이며 서로 다른 실제 명함 200장의 성능으로 표현하지 않는다.

독립 카드·장면을 대상으로 한 이항 비율은 Wilson 95% 구간을 참고로 표시한다. 중대 오류 0건인 경우 독립 단위의 한쪽 95% 상한은 `1 - 0.05^(1/n)`으로 계산한다. 같은 카드 사진에서 한 번이라도 중대 오류가 있으면 그 카드의 오류 사건은 1로 집계한다.

| 독립 단위 n | 오류 0건일 때 한쪽 95% 상한 |
| ----------- | --------------------------- |
| 20          | 약 13.91%                   |
| 100         | 약 2.95%                    |
| 300         | 약 0.994%                   |

따라서 사진 20장에서 오류가 없었다고 실제 오류율 1% 이하를 입증했다고 보고하지 않는다. 실제 명함 없음 0/300은 독립 장면·표본 수집 조건에서 1% 미만 상한을 확인하는 기준이다. 다양한 사용자를 대표하는 표본인지 여부는 별도 조건이며 이 수치만으로 모든 사용 환경을 보장하지 않는다.

### 기존 구현 대비 개선과 모델 선택

1. 필수 품질 기준에 미달한 모델은 최종 기본 후보에서 제외한다. 상대적으로 좋아졌다는 이유만으로 통과시키지 않는다.
2. 기존 외곽 실패율이 ≥5%이면 실패 건수 상대 감소 ≥50%를 추가 개선 목표로 둔다. 기존 실패율이 <5%이면 새 중대 오류 0건과 성공·채택률 비열화를 확인한다. 평균 코너 오차가 기존에 목표를 초과했다면 ≥30% 감소를 개선 목표로 보고한다.
3. 최종 채택률 ≥95%를 충족하고, 기존 대비 채택률 차이의 카드 단위 95% 구간 하한 ≥0을 최종 비열화 확인 기준으로 둔다. 파일럿에서 구간이 넓으면 유의한 개선으로 표현하지 않는다.
4. 품질이 동등한 후보에서 전체 반복 p95 ≥15% 단축 또는 전체 자산 전송 ≥20% 감소가 확인되면 경량 후보 채택을 우선한다. 품질·안정성 gate는 그대로 적용한다.
5. 개선율과 시간이 목표에 미달하면 후보 이름·실패 조건을 기록하고 기준을 낮추지 않는다. 모델 추가 학습·서버 추론·UVDoc 적용은 실패 원인에 맞춘 후속 작업으로 제안한다.

## 12 결과 파일과 보고 형식

예정 평가 스크립트는 `scripts/card_recognition/` 아래에서 data 검사, 공식 기준 비교, 브라우저 benchmark, 결과 판정으로 나눈다. 측정 JSONL·요약 JSON·CSV·이미지 비교·HTML 보고서는 Git 제외 평가 출력 경로에 저장한다. 실행기는 필수 FAIL 시 실패 exit code를 반환하고 표본 부족·미측정은 PASS와 구분한 상태를 낸다.

각 행에는 runId·기준 Git 상태/patch 해시·dataset/model/runtime 해시·기기·브라우저·cache 상태·imageId·조건·입력 크기·소스 종류·결과 상태·코너·비율 출처·품질 지표·구간 시간·실패 이유·자산 크기를 넣는다. 이미지의 연락처 원문은 시간 로그에 넣지 않는다.

최종 요약은 다음 열을 사용한다.

| 모델과 기기  | 데이터 수             | Emean 평균과 p95 | IoU p5 | 잘림 수 | 수정 없는 채택 | warm p50/p95/p99 | cold p95 | 오류/timeout | 버퍼 peak       | 품질 | 성능 | 안정성 | 데이터 |
| ------------ | --------------------- | ---------------- | ------ | ------- | -------------- | ---------------- | -------- | ------------ | --------------- | ---- | ---- | ------ | ------ |
| 실행 후 기록 | 정상/부정/재촬영 분리 | %                | 비율   | 건/전체 | 건/전체와 %    | ms               | ms       | 건/요청      | MiB와 측정 범위 | 상태 | 상태 | 상태   | 상태   |

품질 최악 10개와 가장 느린 10개 입력, 모든 내용 잘림·오검출·시간 초과를 별도 목록에 넣는다. 최소/평균 값만으로 최종 보고하지 않는다. gate마다 기준·측정값·차이·PASS/FAIL/NOT_RUN/INSUFFICIENT_DATA를 한 행으로 남긴다.
