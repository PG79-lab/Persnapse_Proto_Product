## 2. 목표와 작업 범위

**기존 통합 앱과 데이터를 보존하면서 Graph를 주요 탐색 공간으로 만들고, 제품 전체 UI를 하나의 디자인 체계로 정리한다.**

사용자가 다음 세 질문에 답할 수 있어야 한다.

1. 이 사람이 누구였지? — 만남·행사·주제로 기억을 회수한다.
2. 왜 연결되지? — 관계 의미·날짜·실제 원문을 확인한다.
3. 지금 무엇을 하지? — 기록된 약속과 관련 맥락으로 행동을 판단한다.

| 작업 축              | 결과물                                                                                  |
| -------------------- | --------------------------------------------------------------------------------------- |
| 제품 전체 프론트엔드 | 일관된 앱 셸·디자인 토큰·공통 컴포넌트·정보 위계·반응형·상태 표현                       |
| Graph Network        | 목적별 부분 그래프, 공통 선택, 관계 근거, 중심 이동, 선택적 확장·접기·복귀, Recall 연결 |

기존 Next.js·React·D3 및 PostgreSQL 저장 모델을 활용한다. 명함 보정·OCR, 음성 전사, Recall 모델·검색 알고리즘은 기존 처리를 재사용하며 사용자 접근·검토·탐색 경험을 연결한다.

이번 범위에 자동으로 포함하지 않는 항목: Graph DB, 3D, 신규 CRM, native 앱, 이메일·메시지 자동 전송, 외부 캘린더 연동, 공개 배포, AI 어시스턴트 검색 엔진의 전면 재작성. 기존 기능 삭제를 뜻하지 않는다.

## 4. 앱 구조와 화면 설계

### 4.1 Graph 중심 진입

**검토 제안:** `/`에 화면 지정이 없으면 관계 탐색으로 진입한다. 기존 hash 주소와 여섯 기능의 접근 경로는 유지한다.

| 화면      | 주소           | 역할                                 |
| --------- | -------------- | ------------------------------------ |
| 관계 탐색 | `/#map`        | 주요 탐색 공간: 목록·Graph·Inspector |
| 인맥      | `/#people`     | 전체 인맥 조회·정렬·편집             |
| 만남      | `/#meetings`   | 만남 기록·참석자·맥락 관리           |
| 업무      | `/#todos`      | 약속·할 일·일정·브리핑               |
| 명함      | `/#cards`      | 기존 촬영·보정·OCR·검토·저장         |
| 녹음      | `/#recordings` | 기존 녹음·전사·메모                  |

Graph에서 인물을 선택하면 같은 화면의 Inspector를 변경한다. 편집·긴 기록이 필요할 때 확장 상세를 연다. 기존 독립 페이지를 다시 만들지 않는다.

**조정할 작업 규칙:** 현재 `AGENTS.md`는 검색·텍스트 기록을 `/#todos` 어시스턴트에서 수행하도록 명시한다. Graph 안에서 Recall을 연결하는 새 방향과 조정이 필요하다. 구현 시 이를 명시적인 제품 결정으로 기록하고 규칙을 함께 갱신한다. 기존 업무 화면의 어시스턴트 접근도 유지한다. 이번 문서에서는 해당 규칙을 수정하지 않았다.

권고 선택은 실행 설계의 D01~D04에 통합했다. Graph 기본 진입·통합 검색·읽기 API·P0 경계를 최종 검토 묶음으로 제시하며, 최종 OK 시 포함한 결정과 작업 범위를 기록한다. 이 설계 보완만으로 제품 결정·AGENTS가 승인·변경된 것으로 취급하지 않는다.

### 4.2 세 영역 워크스페이스

| 영역           | 구성                                                       |
| -------------- | ---------------------------------------------------------- |
| 좌측 탐색      | 보기 선택, 사람·맥락 목록, 검색 결과, 필터, 결과·표시 범위 |
| 중앙 Graph     | 현재 중심·조건, 관련 노드·관계, 확장·복귀·보기 맞춤        |
| 우측 Inspector | 선택 대상의 프로필·관계 의미·기억·원문·행동                |
| 공통 헤더      | 현재 위치, 전역 검색, 주요 추가 행동, 저장·연결 상태       |

앱 내비게이션과 탐색 목록을 각각 넓은 열로 만들지 않는다. 내비게이션은 접을 수 있게 하고 탐색의 좌측 영역과 통합된 구조를 검토한다.

Inspector는 하나의 해석 패널이며 여러 drawer를 겹치지 않는다.

- 인물: 이름·소속 → 연결 이유 → 관련 기억·원문 → 약속·다음 행동.
- 관계: 관계 의미 → 양 끝 대상 → 날짜·기록 → 원문.
- 행사·주제: 맥락 설명 → 관련 인물 → 개별 기록.
- Recall: 짧은 답변 → 관련 사람 → 이유·근거 → 제안 행동.

## 5. Graph 데이터 설계

### 5.1 책임 분리

`기존 DB/API → 화면용 어댑터 → 부분 그래프 선택 → 탐색 상태·배치 → Graph·목록·Inspector`

| 요소       | 데이터 기준                   | 표현                                         |
| ---------- | ----------------------------- | -------------------------------------------- |
| 사람       | Person ID                     | 이름·소속·식별 단서                          |
| 만남       | Interaction ID                | 개별 만남·대화·날짜                          |
| 행사       | Event ID                      | 여러 만남이 속한 행사 맥락                   |
| 주제       | Topic ID와 확인된 연결        | 해당 주제가 기록된 만남                      |
| 회사       | Organization ID와 Affiliation | 현재·과거 소속 구분                          |
| 약속·할 일 | 기존 Action/Todo              | 기본은 Inspector, 행동 보기에서 필요 시 노드 |

행사와 만남은 별개다. 행사명·회사명 문자열만으로 병합하지 않는다. 타입별 ID를 사용해 다른 종류의 엔터티가 같은 렌더러 ID로 충돌하지 않게 한다.

참석·대화·소속·소개·공유 맥락의 의미를 유지한다. 주제가 포함된 만남의 참석을 특정 인물의 관심 표현으로 승격하지 않는다. 소개는 현재 데이터가 담은 방향과 해석 한계를 표시한다.

### 5.2 관계 신뢰성

| 구분        | 의미                                                       |
| ----------- | ---------------------------------------------------------- |
| 기록된 관계 | 저장된 만남·소속·소개·대화 기록으로 확인 가능              |
| 공유 맥락   | 각각 같은 행사·회사·주제에 연결됨. 실제 친분을 뜻하지 않음 |
| 제안·추론   | 검토할 해석으로 기본 사실과 분리                           |

확인 상태와 추론 여부는 별개다. `confirmed`는 사용자 검토 상태이며 외부 사실 검증을 뜻하지 않는다. 관계별 근거를 보존하고 날짜 필터에 따라 해당 기간의 근거·집계를 다시 계산한다.

### 5.3 조회 계약 확장

현재 workspace snapshot은 인물·만남·참석·소개·업무를 제공하지만 행사·주제 ID, 참석자 역할, 소속 기간, 관계별 출처는 충분히 전달하지 않는다.

1. 기존 snapshot으로 인물·만남 탐색을 먼저 완성한다.
2. 기존 DB를 읽는 Graph 조회 계약을 추가해 행사·주제·소속·근거를 확장한다.

두 번째 단계는 **읽기 API 확장 제안**이다. [Graph 계약 5~7장](04-frontend-graph-contracts-2026-10-15.md)에 GET endpoint 후보·타입·응답 예시·페이지·근거 상태·오류를 구체화했다. W06에서 현재 repository·접근 경계·schema 매핑 적합성을 확인한 뒤 W07을 구현한다. DB 스키마 변경을 기본 전제로 삼지 않는다.

조회 계약에 필요한 정보:

- 타입이 구분된 노드·엣지 ID 및 기존 레코드 ID 대응.
- 관계 종류·방향·근거 참조와 관계별 확인 상태.
- 발생 시점·기록 시점·날짜 정밀도. 날짜 미정 보존.
- 출처 접근 상태: 제공됨·부재·삭제·접근 불가·조회 실패의 구분.
- 결과 노드와 설명용 맥락 노드의 구분.
- 추가 항목 존재 여부, 정확하게 계산한 경우의 전체 개수.

전체 원문은 초기 응답에 모두 넣지 않고 선택 시 필요한 근거를 조회한다. 모든 조회는 기존 workspace 접근 경계를 적용한다. 다른 workspace의 존재·개수가 집계로 노출되지 않게 한다.

| `selection`       | 지금 읽는 노드·관계      |
| `focus`           | 현재 부분 그래프 중심    |
| `view`            | 사람·행사·주제 등의 보기 |
| `filters`         | 기간·종류·상태·중요도    |
| `expansion`       | 어떤 관계를 펼쳤는지     |
| `history`         | 논리적 탐색의 이전 상태  |
| `viewport/layout` | 확대·화면 위치·좌표·고정 |
| `query`           | 입력 초안·제출 질문·결과 |
| `draft`           | 작성·수정 중인 기록      |

새 상태 라이브러리는 우선 추가하지 않고 reducer·context 등 기존 구조에 맞는 최소 장치를 사용한다. 서버 데이터 저장소와 화면 탐색 상태를 구분한다.

### 동작 규칙

- 선택: 상세·연결 강조만 변경하며 배치·카메라 유지.
- 중심 이동: 명시적 버튼으로 실행하고 이전 탐색 저장.
- 확장: 종류·범위를 안내하며 관련 항목만 추가.
- 접기: 다른 확장이나 선택에서 필요한 노드를 유지. 확장별 참조를 관리.
- 복귀: 중심·필터·확장·선택·좌표·확대 수준 복원.
- 빈 영역 클릭: 선택만 해제. 중심·필터·질문 초기화 금지.
- 데이터 갱신: 삭제된 대상은 접근 불가로 표시하고 작성 초안 보존.

탐색 이력과 데이터 수정 Undo는 분리한다. 포인터 이동·매 프레임 카메라 변화는 이력에 넣지 않는다. 초기 P0에서는 세션 내 복귀를 우선하며 재방문 영속 복원은 개인정보·workspace 범위를 확인한 별도 설계로 다룬다. 민감한 질문·원문을 URL에 직렬화하지 않는다.

요청 revision과 레코드 version을 사용해 늦은 질의·확장·근거 응답이 현재 선택·필터·편집을 덮어쓰지 않게 한다. Abort만으로 해결된다고 가정하지 않는다.

구체 상태 소유권·이력 포함 항목·필터 밖 선택·중첩 참조·삭제 reconcile·모바일·저장 전이는 [Graph 계약 3~~4장의 T01–T12](04-frontend-graph-contracts-2026-10-15.md)를 따른다. 선택 marker와 Inspector 열림은 별도 상태다. 계약은 아직 구현·테스트된 것이 아니다.

## 7. 표시 범위와 배치

현재의 인맥 8명 페이지 표시·만남 10개 초과 시 숨김을 목적별 부분 그래프 방식으로 발전시킨다.

| 보기      | 표시 기준                         |
| --------- | --------------------------------- |
| 인물 중심 | 선택 인물과 관련 만남·주제·소속   |
| 행사 중심 | 행사와 개별 만남·참석 인물        |
| 주제 중심 | 주제가 기록된 만남과 인물         |
| 전체 보기 | 제한된 표시 범위와 추가 탐색 경로 |

첫 화면은 최근 저장된 실제 기록 등 설명 가능한 기준으로 대상을 제시한다. 관계 기록이 없는 인물은 가짜 `나–인물` 선을 만들지 않고 독립 인물로 접근한다.

타입별 안정된 ID로 좌표를 재사용한다. 새 노드는 연결된 맥락 근처에 배치하고 사용자가 고정한 위치를 유지한다. 시뮬레이션은 안정화 후 정지한다. 렌더러가 도메인 원본 객체를 변경하지 않게 한다.

표시 한도는 성능 측정으로 결정한다. 선택·검색 결과·설명에 필요한 근거를 우선하며 생략 범위를 알린다. 검색 결과 전체 수와 현재 지도 표시 수를 구분한다. 알 수 없는 전체 수를 임의로 표시하지 않는다.

## 8. 검색·입력·행동 연결

### 8.1 검색과 Recall

| 입력             | 처리                  |
| ---------------- | --------------------- |
| 이름·회사·연락처 | 기존 결정적 검색      |
| 자연어 맥락 질문 | 명시적 제출 시 Recall |
| 현재 보기 조건   | Graph 범위 필터       |

검색 진입점을 통합하되 전체 데이터 검색과 현재 보기 범위를 표시한다. 모든 키 입력마다 LLM을 호출하지 않는다.

Recall 결과의 `personId`로 선택하고 제공된 evidence를 Inspector에 표시한다. 현재 응답만으로 원본 행사·주제·만남 ID를 확인할 수 없으면 Graph 경로를 만들어내지 않는다. 확인 가능한 근거만 표시하고 필요한 조회 계약을 연결한다. evidence의 표시 제목이나 본문을 파싱해 인물·엔터티 ID를 추측하지 않는다.

오래된 요청은 최신 결과를 덮어쓰지 않는다. 선택 변경에도 질문 초안과 대화 표시 상태를 유지한다. 대화 상태 보존은 기존 엔진이 이전 대화를 이해한다는 뜻이 아니다. 연속 대화·검색 엔진 고도화는 별도 후속 범위다.

### 8.2 입력과 저장

`입력 → 검토·수정 → 인물 확인 → 저장 → 변경 대상 열기`

명함·텍스트·음성의 기존 처리와 commit을 재사용한다. 명함의 감지·보정·회전·OCR 경로와 음성 녹음·전사 기능을 보존한다.

저장 성공 후 최신 서버 상태를 반영하고 추가된 인물·만남·기억만 강조한다. 실패 시 입력을 보존하며 확정 노드가 생긴 것처럼 표시하지 않는다. 저장 전에 preview와 저장 완료 상태를 구분한다. 데이터 수정 Undo는 실제 지원하는 범위에서만 제공한다.

### 8.3 다음 행동

저장된 약속·후속 행동·AI 제안을 구분한다. 기존 업무 모델의 추가·완료·완료 취소를 연결한다. 새로운 AI 제안을 저장하는 경로는 실제 계약이 준비된 경우만 제공한다. 이메일·메시지 자동 전송은 추가하지 않는다.

## 9. 디자인 시스템과 전체 화면 정제

기본 방향: **Calm Professional Context Workspace — 밝고 차분한 업무용 관계 탐색 공간.**

이 장의 구현 판단 기준은 [Visual Design 상세 설계](03-frontend-graph-visual-design-2026-10-14.md)에 정리했다. 전체 개발·데이터 설계는 이 문서를 유지하고, 화면별 시각 명세는 상세 문서를 함께 읽는다.

### 9.1 Persnapse의 정보 위계

사람 식별 → 연결 이유 → 실제 기억·원문 → 저장된 약속·다음 행동 순서로 읽게 한다. Graph는 이 정보를 연결하는 탐색 공간이다. 인물 크기·선 길이·공간적 근접을 관계 강도나 소개 가능성으로 표현하지 않는다.

선택·탐색 중심·키보드 포커스는 서로 다른 표시를 가진다. 기록된 연결·파생 공유 맥락·AI 제안은 선 스타일뿐 아니라 의미 문구와 근거 패널로 구분한다. 사진·원문·관계가 없으면 해당 상태를 표현하고 시각적 완성도를 위해 사실을 채워 넣지 않는다.

### 9.2 공통 디자인 체계

| 항목      | 적용 설계                                             |
| --------- | ----------------------------------------------------- |
| 색상      | 기존 색을 배경·본문·선택·관계·상태 의미 토큰으로 통합 |
| 타이포    | 현재 한국어 폰트 유지, 이름·본문·메타데이터 위계 정리 |
| 컴포넌트  | 버튼·목록 행·패널 헤더·필터·근거 행·입력·상태 공통화  |
| Graph     | 기본 인물 크기는 균일하게, 중요도는 표시·필터로 보존  |
| Inspector | 섹션과 얇은 구분선 중심, 긴 원문 확장 지원            |
| 모션      | 선택 강조·짧은 중심 이동·저장 후 국소 강조            |
| 모바일    | 목록 전환·상세 패널, 작성 상태·스크롤·복귀 유지       |

보라색은 선택·포커스·주 행동에 집중한다. 과도한 카드·배지·그림자·무의미한 수치 요약을 줄이되 필요한 설명·상태·행동은 유지한다.

현재 `experience.css`의 보라색 `#7040CA`·중립색·시스템 폰트를 출발점으로 삼는다. 세 CSS 레이어와 전역 스타일의 변수·컴포넌트 중복을 의미 토큰으로 정리하고 기존 lucide 아이콘 체계를 유지한다. 선언된 폰트와 실제 로딩된 폰트를 구분한다.

상세 설계에는 색상 역할·초기값·색상 쌍 대비 계산, 타이포 크기·행간·굵기, 간격·radius·버튼·hit target·레이어 기준을 제시했다. 전체 제품 접근성이 검증되었다는 뜻은 아니다.

상세 설계 5.5장은 고정 원칙·기본 구현값·Codex 조정 범위·제품 결정의 강도를 구분한다. 치수는 우선 적용할 기본값으로 사용하고 실측에 근거해 허용 범위 안에서 조정·기록한다. 최종 브랜드 검증 완료를 뜻하지 않는다. 긴 한글·영문 혼용·동명이인·사진 없음·원문 없음·오류 상태에서 검증하며 기존 CSS 변수와 아이콘 체계를 우선 재사용한다.

`workspace.css`, `integration.css`, `experience.css`의 역할·충돌을 조사한 뒤 점진적으로 정리한다. 새로운 override를 계속 덧붙이는 방식은 피한다.

### 9.3 화면별 상세 명세

| 상세 설계 위치 | 구체화한 내용                                                                     |
| -------------- | --------------------------------------------------------------------------------- |
| 5~6장          | 토큰·타이포·공통 치수, 1440px 기준 좌 240/중앙 가변/우 360, 작은 폭에서 영역 전환 |
| 7~10장         | 타입별 노드, 선택·중심·고정, 기록·공유·제안 선, 라벨·Semantic Zoom·확장·복귀      |
| 11장           | 인물·관계·맥락 Inspector, 원문 읽기 폭, 편집 draft·선택 변경                      |
| 12~13장        | 검색·Recall 결과·AI 답변, 명함·음성·텍스트 검토·저장 상태                         |
| 14~18장        | 기존 전체 화면 정제, 공통 컴포넌트 상태, 오류·모바일·키보드·모션                  |

## 10. 실행 단계와 의존성

아래 1~~8은 작업 영역의 큰 분류다. **실제 실행 순서·의존성·완료 증거는 실행 설계 3장의 W00–W11 표로 통일한다.** 핵심 3화면의 예비 시안을 먼저 비교하고, 계약 연결 후 통과한 화면을 기준으로 전체 화면을 확장한다.

| 단계               | 작업                                                   | 종료 조건                                 |
| ------------------ | ------------------------------------------------------ | ----------------------------------------- |
| 1. 기준 확정       | 기존 기능·UI·변경 파일 목록, 참조 화면, 회귀 대상 정리 | 보존 기능과 개선 화면이 명확함            |
| 2. 디자인 기반     | 토큰·공통 컴포넌트·앱 셸·반응형 골격                   | 세 영역의 위계·가독성 확보                |
| 3. 최소 Graph 흐름 | 인물·만남 어댑터, 공통 선택, Inspector                 | 목록→Graph→상세가 같은 ID, 실제 기록 접근 |
| 4. 탐색 완성       | 중심 이동·확장·접기·복귀·위치 고정                     | 중첩 확장·복귀에서 상태·배치 유지         |
| 5. 맥락·근거 확장  | Graph 읽기 계약, 행사·주제·소속·관계 근거              | 각 연결의 의미·근거 확인                  |
| 6. 제품 흐름 연결  | Recall·입력·저장 결과·업무 연결                        | 검색→근거→행동, 입력→저장→탐색 동작       |
| 7. 전체 화면 정제  | 인맥·만남·업무·명함·녹음·설정 일관성                   | 기존 기능 접근·동작 보존                  |
| 8. 검증·수정       | 기능·디자인·모바일·접근성·회귀 검증                    | P0 수용 기준과 실제 증거 확보             |

각 W 작업에서 동작과 시각 증거를 확인한다. V3a는 기존 인물·만남·참석, V3b는 조회 계약 이후 행사·주제·소속·공유 맥락이다. V4a/V5a 시안과 V4b/V5b 실연결을 구분한다. 선행 계약이 없는 필수 항목은 통과가 아니라 계약 의존으로 기록한다.

디자인 반복 대상은 **Network 기본·인물 선택 / Recall 검색 결과·근거 / 명함·맥락 입력 검토**다. 한 번에 모든 화면을 만들고 마지막에만 검토하지 않는다.

시각 작업은 상세 설계 20장의 V0–V7 단위로 진행한다. 단계 2~~3에서는 셸·공통 상태·Network/Person을 먼저 비교하고, 단계 4~6에서는 관계 근거·Recall·입력 검토의 동일 시각 문법을 검증한다. 화면 캡처만으로 데이터·저장 계약 검증을 대체하지 않는다.

각 작업 검토에는 atlas 4~~8장의 `레퍼런스 crop / 구축물 before / 구축물 after`와 전체 화면, 고정 재현 조건, 구체 문제·수정·재검증·미해결 항목을 남긴다. 한 반복은 관련 문제 1~~3개에 집중한다. 참조 이미지와 비슷해진 정도 대신 Persnapse의 읽기·관계 의미·실제 행동·상태 보존을 판정한다.

## 11. 검증 설계

### 11.1 합성 데이터

동명이인·반복 만남·동명 행사·과거 소속·날짜 미정·삭제된 근거·많은 이웃·늦은 응답을 포함한다. 기존 fixture 구조를 활용하고 실제 인맥·명함·음성을 fixture나 공개 캡처에 넣지 않는다. 날짜 시나리오는 테스트에 기준 시간과 `Asia/Seoul`을 주입한다.

실행 설계 6장의 FG-FIXTURE-01을 구현 기준으로 사용한다. 설명 별칭과 실제 UUID를 한 곳에서 매핑하고 코드 파일·해시는 생성 후 기록한다. 현재 실행 가능한 새 fixture가 작성된 상태는 아니다.

### 11.2 필수 확인

- 선택 전후 카메라·기존 좌표 유지.
- 목록·Graph·Inspector의 대상 ID 일치.
- 공유 맥락에서 친분 관계 생성 금지.
- 관계별 근거 또는 명시적 근거 부재 확인.
- 중첩 확장·접기·복귀와 고정 위치 보존.
- 필터 밖 검색 결과 접근 및 결과/표시 범위 구분.
- 늦은 응답·저장 충돌·삭제된 대상 처리.
- 입력 수정·저장·재시도와 기존 회귀.
- 모바일·키보드·200% 확대·reduced motion.
- Graph 오류 시 목록·상세 접근.

단위 테스트는 ID·관계 의미·slice·확장 참조·날짜에 집중한다. 통합 테스트는 공통 선택·지연 응답·충돌·저장 후 갱신을 확인한다. 브라우저 테스트는 실제 클릭·입력·복귀·실패 복구를 확인한다.

### 11.3 시각 검증

초기 viewport: 1440×900, 1280×800, 1024×768, 768×1024, 390×844, 360×780. 고정 breakpoint 지시가 아니라 검증 출발점이다.

캡처 상태: 빈 화면·기본 Graph·인물 선택·관계 근거·검색 결과·AI 답변·입력 검토·오류 복구·모바일 상세. 실제 동작 중인 화면에서 합성 데이터로 생성한다.

수정 순서: 기능·데이터·입력 손실 차단 → 접근성·가독성·상태 보존 → 공통 컴포넌트·정렬·밀도 → 미세 모션. 사용자·디자인 관점과 개발·QA 관점을 각각 검토하고 발견 문제·수정·재검증을 기록한다.

[상세 설계 21장](03-frontend-graph-visual-design-2026-10-14.md)의 상태별 Pass 기준을 함께 사용한다. 특히 선택과 중심의 구분, 원문 부재·삭제·조회 실패, 저장 미확인·충돌, 동명이인·긴 텍스트, 모바일 sheet·복귀를 같은 합성 데이터로 재현한다. 22장의 대응표로 두 번째 브리프의 Visual Spec·Visual QA 반영 여부를 추적한다.

atlas의 VS01–VS12 화면 상태 ID와 관찰표를 사용해 작업에 필요한 before/after·영역 crop·전환 증거를 생성한다. 원본 브리프 S01~~S12는 GS01~GS12로 인용하며 Atlas 6.2 대응표로 구분한다. 외부 홍보 이미지의 DPI·프레임·부분 흐림을 제품 치수나 접근성 통과 근거로 사용하지 않는다. 아직 생성하지 않은 구축물 캡처를 문서의 완료 증거로 연결하지 않는다.

### 11.4 명령과 성능

제품 구현 단계의 기본 검사: `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`. 단계 종료 시 저장소 규칙의 필수 검사를 완료하고 최종 `npm run verify` 및 적절한 브라우저 E2E를 수행한다.

새 worktree의 격리 실행은 실행 설계 5장을 따른다. 전용 config·port·reuse false·소스 식별·미등록 API 차단을 W00에서 준비한다. 기존 기본 3000 포트와 서버 재사용 설정을 그대로 사용해 다른 worktree를 검증하지 않는다. 명령 예시는 필요한 config가 구현된 후에만 유효하다.

`dev`, `build`, E2E는 빌드·런타임 산출물을 생성할 수 있으므로 이번 문서화 단계에서는 실행하지 않았다. 실제 DB 쓰기·유료 모델을 사용하는 검증은 mock 검증과 구분한다.

성능은 API 응답·어댑터·배치·렌더링 시간을 나누어 측정한다. 첫 표시, 안정화, 선택, 확장, 패널 열기, pan/zoom 지연, idle 계산 여부를 확인한다. 저장 규모·표시 노드/선 수·기기·브라우저·반복 횟수를 기록한다. 실측 전 성능 SLA나 렌더러 교체 필요성을 단정하지 않는다.

## 12. 완료 기준과 후속 범위

**P0 완료:** 검색·선택·근거·확장·복귀·입력·행동이 실제 데이터 경로로 연결되고, 기존 기능과 데이터가 보존되는 상태.

대표 완료 흐름:

`검색·목록 → 사람 선택 → Graph·상세 일치 → 실제 근거 확인 → 맥락 확장 → 복귀 → 행동 또는 기록`

| 단계 | 범위                                                                                              |
| ---- | ------------------------------------------------------------------------------------------------- |
| P0   | 공통 디자인·셸, 집중 Graph, 선택 동기화, 관계 근거, 확장·복귀, 기존 입력·저장·행동, 모바일·접근성 |
| P1   | Recall Path 강화, 새 기억의 국소 피드백, Action Lens 강화, 두 대상의 공통 맥락 비교, 저장된 보기  |
| P2   | 시간 기반 Graph 탐색, 검증된 소개 경로, 고급 군집·필요한 성능 최적화                              |

현재 설계에서 검토할 핵심 결정은 **Graph 기본 진입, 통합 검색·Recall 배치, 기존 DB를 활용한 읽기 API 확장**이다. P1·P2를 P0의 가짜 기능이나 샘플 전용 성공 상태로 대체하지 않는다.

P0 필수 항목의 계약 의존·미검증은 완료가 아니다. 지원 불가 범위는 계약을 해결하거나 사용자 범위 변경을 기록한다. 최종 시각 기준은 Visual Design의 VD01–VD03 채택 결과와 상태별 증거이며 외부 이미지 유사도가 아니다.

완료 보고에는 실제 변경, 보존 규칙, 참조 패턴, 실행한 검사, 브라우저 캡처, 계약의 제한, 미검증 항목과 후속 과제를 구분한다.

## 13. 이번 문서화의 결과

초기 문서화에서 이 작업 설계를 추가했고, v0.2에서는 Visual Design 상세 설계를 추가했다. v0.3에서는 Reference Atlas·반복 개선 검토 설계를 추가하고 기존 두 문서를 보강했으며 공식 참고 이미지 31개와 manifest를 문서용으로 저장했다. 원본 브리프는 복제하지 않았다. 기존 미커밋 변경, 제품 코드, 작업 규칙, DB, 환경 설정, 배포 상태는 변경하지 않았다. 제품 구현·테스트·빌드와 구축물 before/after 캡처는 아직 진행하지 않았다.

v0.4는 새 review worktree에서만 설계를 보완했다. 실행 설계와 Graph 계약을 추가하고 기존 세 문서의 강도·단계·ID·검토 우선순위를 정합화했다. 실제 시안·API·테스트 설정·fixture 구현은 여전히 미착수이며 원본 worktree 문서는 동기화하지 않았다.
