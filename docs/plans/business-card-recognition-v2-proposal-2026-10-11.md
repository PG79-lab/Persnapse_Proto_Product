# 명함 인식 고도화 계획 — 2026-10-11

상태: **단일 명함 1차 구현 중**. 실제 카메라 촬영 명함 약 20장의 위치와 정답은 추후 전달된다. 이 자료가 없으므로 OCR 정확도, 시각적 유사도, p95 지연은 아직 평가하지 않았다. 제품 결정은 [ADR 0019](../decisions/0019-business-card-recognition-v2.md), 기술 후보 조사는 [연구 기록](../research/business-card-recognition-v2-2026-10-11.md)을 따른다.

## 목표와 사용자 흐름

2026-10-12부터 프론트 개발·검증 대상은 통합 워크스페이스의 `/#cards`로 통일한다. 독립 명함 페이지와 별도 명함 모달은 제거했으며, 통합 페이지의 같은 등록 흐름을 유지한다. 현재 연결·브라우저 검증은 [운영 기록](../operations/card-recognition-local-validation-2026-10-11.md)의 2026-10-12 항목을 따른다.

| 단계      | 사용자 경험                                                                                                                                                             | 보존되는 상태                                                                                                |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 촬영      | 카메라 버튼에서 후면 카메라를 열고 그리드 없이 단일 명함을 촬영한다. 재촬영과 이미지 업로드도 제공한다.                                                                 | 전체 프레임 기반 원본 역할 자산과 표시용 자산을 비공개로 저장한다. 최초 권한과 재요청은 브라우저가 결정한다. |
| 필드 확인 | 이름·조직·직책·전화·이메일 등을 확인하고 수정한 뒤 `OK`를 누른다.                                                                                                       | 수정한 필드와 확인 시점을 초안에 저장한다. 사람·관계 기억은 생성하지 않는다.                                 |
| 명함 결과 | 촬영 이미지를 즉시 보고, 평면 보정 후보가 준비되면 글자와 로고가 잘리지 않았는지 확인한다. 자동 감지가 틀리면 네 모서리를 직접 지정한다. 보정 후보를 승인하면 저장한다. | 원본 사진, 확인한 필드, 보정된 표시용 이미지를 분리한다. 보정에 실패하거나 거절하면 촬영 이미지를 유지한다.  |
| 관계 기억 | 만남 맥락을 구조화하고 인물 후보를 선택한 뒤 별도로 저장한다.                                                                                                           | 기존 원자적 commit 경계를 유지한다. 확인된 명함 초안은 새로고침 후 재개할 수 있다.                           |

명함 결과는 **보기 전용**이다. 전체 카드 이동, 확대와 원본 전환을 제공한다. 텍스트를 HTML로 덮어 쓰는 편집형 카드는 목표가 아니다. 사용자가 수정한 연락처는 구조화 필드에만 반영하고 명함의 인쇄면을 임의로 바꾸지 않는다.

## 현재 구현 범위

- 기존 카메라의 안내 테두리를 제거하고 `ImageCapture.takePhoto()`가 실패하면 비디오 전체 프레임을 사용한다.
- 기존 CLOVA General/OpenAI 추출, Zod 계약, 비용 예약, 캐시, 멱등성을 재사용한다. OCR은 원본 역할 이미지를 입력한다.
- 별도 `card_recognition` 모듈에서 OpenCV.js를 지연 로딩해 사각형을 찾고 원근 변환한다. 자동 결과는 미리보기 확인 후 저장한다. 수동 네 모서리 지정과 촬영 이미지 유지 경로를 제공한다.
- `fields_confirmed_at` 마이그레이션과 필드 확정 API, 확인된 초안 목록/재개 API, 복원 이미지 저장 API를 추가한다. 맥락 분석과 commit은 확인된 필드만 사용하도록 서버 경계를 둔다.
- 원본 디자인을 보존하는 1차 시각 결과는 **보정된 실제 이미지**다. 생성형 업스케일링·로고 재합성·서체 재구성은 아직 적용하지 않았다. 실제 명함으로 텍스트 선명도와 디자인 일치도를 측정한 뒤 더 강한 복원 방식을 비교한다.

## 평가

| 영역      | 측정 방법                                                                                                | 판단                                                                     |
| --------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| OCR       | 같은 실제 사진과 검수 정답으로 이름·회사·직책·전화·이메일의 값 단위 오탐, 누락, 장당 수정 수를 비교한다. | 정확성을 우선하며 잘못된 전화·이메일이 늘어나는 후보는 채택하지 않는다.  |
| 평면 복원 | 원본과 보정본을 나란히 보고 명함 전체 포함, 글자/로고 잘림, 코너 오류, 수동 조정 횟수를 기록한다.        | 자동 적용 조건과 원본 fallback 기준을 정한다.                            |
| 시각 결과 | 배치·색·글자 선명도·로고·장식의 원본 유사도를 사람이 검수한다.                                           | 사진 기반 결과가 부족한 경우에만 업스케일링/디자인 복원 후보를 평가한다. |
| 속도·비용 | 촬영→필드 수정 가능, `OK`→시각 결과, 후보 승인→저장을 구간별 p50/p95와 실패율로 기록한다.                | **p95 3초는 지향 목표**다. 정확도를 해치지 않는 최적화부터 적용한다.     |

실제 사진 약 20장은 파일럿 오류 분석에 사용한다. 제품 수준의 통계에는 다양한 카드와 기기에서 검수한 더 큰 표본이 필요하다. 사진·정답·모델 원문 응답을 Git, 로그, 공유 Preview에 넣지 않는다. 기존 `D:\Persnapse\OCR test`의 공개 영수증/문서 점수를 명함 점수로 옮기지 않는다.

## 후속 작업

1. 실제 명함 사진 경로와 정답 라벨을 받으면 현재 경로의 OCR, 코너 검출, 시각 결과, 모바일 지연을 기준선으로 측정한다.
2. 동일 입력에서 기존 OpenAI/CLOVA와 추가 OCR 후보, 원본/보정 입력을 짝지어 비교한다. 유료 호출과 추가 지연은 품질 이득으로 판단한다.
3. 글자·로고·색을 더 잘 보존해야 할 경우 업스케일링 또는 디자인 복원 후보를 격리 평가한다. 보이지 않는 문자·숫자·로고를 생성하는 후보는 제외한다.
4. 단일 명함 품질을 확인한 뒤 한 사진 안의 다중 명함(약 6장) 분리·인식을 설계한다. 여러 **별도 파일**을 처리하는 기존 큐와 구별한다.
