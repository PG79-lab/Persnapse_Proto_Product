# 명함 인식 품질 스프린트 실행 설계 — 2026-10-08

## 목표와 범위

행사·미팅에서 명함 한 장을 촬영하거나 업로드한 사용자가 정확한 연락처를 빠르게 확인하고, 만남 맥락과 인물 연결을 검토해 관계 기억으로 저장할 수 있게 한다. 우선순위는 **인식 정확도 → 정확도를 유지한 처리 속도 → 촬영·검토·디지털 카드 UX**다. UI 수정은 앞 단계와 병행할 수 있지만, 속도를 위해 정확도를 희생하지 않는다.

현재는 설계 단계다. 새 모델의 우수성이나 목표 시간 달성을 검증한 상태가 아니다. 명함의 글자 인식 오류, 필드 분류 오류, 촬영 손실을 같은 문제로 취급하지 않는다.

### 기준 사용자 시나리오

1. 모바일 웹에서 명함 한 장을 촬영한다. 촬영본을 확인하고 필요하면 다시 찍거나 기존 사진을 선택한다.
2. 이름·회사·직책·전화·이메일이 채워진 카드를 보며 오인식만 수정한다. 없거나 충돌하는 값은 확인 필요로 표시한다.
3. 기존 인물 후보 또는 새 인물을 명시적으로 선택하고, 짧은 만남 맥락을 남긴다.
4. 저장된 디지털 카드의 원본 이미지와 구조화된 정보, 연결된 관계 기억을 확인한다.

## 단계 0 — 기준 데이터와 계측

**구현:** 촬영 확정→브라우저 전처리→업로드→Storage→DB→OCR→응답→수정 화면 표시의 구간별 시간을 기록한다. 실제 카메라 트랙 해상도와 저장 이미지 크기도 개발용 진단에 남긴다. 개인정보·OCR 원문·키는 로그에 넣지 않는다. 후보별 요청 수, 실패율, 비용도 따로 기록한다.

**평가 세트:** 동의를 얻은 실제 명함부터 10장 안팎으로 오류 유형을 찾고, 가능하면 서로 다른 디자인·조명·기기·한/영 명함 20장 이상으로 비교한다. 같은 명함의 웹 촬영본과 휴대폰 기본 카메라 사진을 짝지어 입력 손실을 분리한다. 이름·회사·직책·전화·이메일의 정답과 원래 명함에 없는 필드를 표기한다. 평가에 쓴 명함과 최종 확인용 명함은 구분한다. 실물 데이터가 없으면 합성 테스트는 동작 확인까지만 보고 정확도 결론을 유보한다.

**지표:** 필드별 존재하는 값의 정확 일치율, 없는 값의 허위 생성률, 장당 수동 수정 필드 수, 중요 필드 오류가 남은 저장 건수, 촬영 확정→수정 가능 시점, 구간별 p50/p95. 전화는 국가번호를 보존한 숫자 형식, 이메일은 소문자, 일반 텍스트는 Unicode 정규화와 양끝 공백만 비교용으로 정규화한다. 자동 저장 전 사용자 확인은 유지한다.

**완료 기준:** 같은 입력과 정답으로 기존 경로를 재실행할 수 있고, 카메라 손실·OCR 글자 오류·필드 분류 오류의 비중을 구분할 수 있다. 표본이 작으면 p95를 제품 보장 수치로 표현하지 않는다.

## 단계 1 — 촬영 품질 복구

**구현:** 화면 가이드와 실제 저장 자르기를 동일한 좌표계로 맞춘다. 촬영 직후 저장될 이미지를 보여주고 재촬영을 허용한다. 트랙 `getSettings()`와 비디오 해상도를 비교한다. 지원되는 브라우저에서는 `ImageCapture.takePhoto()`의 고화질 정지사진을 평가하고, 미지원 환경에는 기본 카메라 사진 선택 및 기존 비디오 프레임 경로를 둔다. 브라우저 지원·기기별 결과를 확인하기 전 단일 방식을 강제하지 않는다. 과도한 확대·재압축을 피하고 OCR 입력에 원본에 가장 가까운 변형을 사용한다. 흐림·반사는 간단한 재촬영 안내부터 적용한다.

**완료 기준:** 촬영 가이드 안에 있는 글자가 저장 이미지에서 잘리지 않는다. 같은 명함의 웹 촬영본과 기본 카메라 사진의 핵심 글자 판독 차이를 줄인다. Android Chrome·iPhone Safari·데스크톱 업로드에서 회귀가 없다.

## 단계 2 — 인식·구조화 후보 비교

| 후보                                               | 실험                                                                          | 채택을 가르는 점                                                  |
| -------------------------------------------------- | ----------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| A. 현행 CLOVA General + 규칙                       | 동일한 평가 세트의 기준점                                                     | 속도와 비용 기준. 규칙 추가만으로 해결 가능한 오류인지 확인.      |
| B. CLOVA General + OpenAI 이미지·OCR 텍스트 구조화 | 현재 인식 글자와 명함 사진을 함께 보고 기존 `BusinessCardExtractionV1`로 출력 | 레이아웃 오류 개선 여부, 추가 지연·비용, 숫자·이메일 오기입 여부. |
| C. OpenAI 이미지 직접 추출                         | 명함 사진만으로 동일 스키마 출력                                              | OCR 단계를 생략해도 한글과 정확한 연락처를 더 잘 읽는지.          |
| D. CLOVA 명함 전용 Document OCR                    | 사용 승인을 받을 수 있으면 같은 세트로 비교                                   | 한·영·일 명함 전용 필드 추출의 실제 이득과 도입 시간.             |
| E. Gemini 이미지 구조화 / Google Cloud Vision      | 추가 계정·키가 준비된 경우에만 비교 후보                                      | A~D보다 확실한 이득이 있는지. 새 인프라 비용과 작업 시간을 고려.  |

모든 후보는 동일 이미지·동일 정답·동일 출력 스키마로 비교한다. 생성 모델에는 **이미지에 보이는 값만 기입하고 확인 불가 시 `null` 또는 빈 배열**을 요구한다. 출력 스키마 준수는 사실 정확도를 보증하지 않으므로 이메일·전화 형식 검사와 원문/후보 간 충돌 표시를 별도로 둔다. 모델마다 개인정보를 추가 제공하기 전에 전송 범위를 확인한다. OpenAI·Gemini·CLOVA 전용 방식의 품질 순위는 측정 전까지 미정이다.

**채택 기준:** 현행 대비 중요 필드의 잘못된 값과 장당 수정량이 의미 있게 감소하고, 없는 값을 만들어내는 비율은 증가하지 않아야 한다. 1차 목표는 중요 필드 수정량 50% 감소다. 일부 명함에서만 추가 모델이 필요하면 누락·형식 오류·후보 충돌이 있는 경우에만 호출하는 경로를 비교한다. 후보가 기준을 넘지 못하면 기존 CLOVA 경로를 유지한다. 실제 응답·원본 이미지의 비공개 저장, 사용자 수정 우선, 자동 인물 병합 금지, 중복 유료 호출 방어를 보존한다.

## 단계 3 — 검토 및 디지털 카드 UX

**사용자 흐름:** `촬영/선택 → 실제 잘린 이미지 확인 → 핵심 5개 필드 수정 → 만남 맥락·인물 연결 확인 → 저장`. 촬영창은 촬영 성공 후 닫고 처리 상태는 작업 화면에서 보여준다. 필수 정보는 먼저, 주소·웹사이트·부서 등은 펼쳐서 검토한다. 비어 있거나 형식 검사에 실패하거나 후보가 충돌한 필드만 `확인 필요`로 표시한다. 점수 근거가 없는 상태에서 가짜 신뢰도를 표시하지 않는다. 원본 이미지는 가리지 않고 확대해 볼 수 있게 하고, 디지털 카드의 정보 면은 선명한 텍스트와 전화·메일 동작을 제공한다.

**완료 기준:** 모바일에서 사용자가 원본을 확인하며 필수 필드를 수정할 수 있고, 실패 후 같은 Capture로 재시도할 수 있다. 기존 인물 연결과 맥락 저장의 명시적 확인은 유지한다. 저장 후 Profile의 카드·연락처·관계 기억이 일치한다.

## 단계 4 — 정확도 유지 조건의 속도 개선

단계 2의 채택 경로를 고정한 뒤 단계 0의 최장 구간부터 줄인다. 우선 검토 항목은 중복 이미지 인코딩, original/display 순차 Storage 업로드, 불필요한 서버 왕복, 조건부 추가 모델 호출이다. Storage 병렬화나 OCR 선행 실행은 부분 실패 정리·재시도·멱등성을 함께 검증한 경우에만 적용한다. 캐시 적중과 미적중의 지연을 따로 보고, 5초 지연 안내와 서버 전체 제한을 실제 동작과 맞춘다.

**완료 기준:** 같은 평가 세트에서 단계 2의 정확도·허위 생성·수정량이 악화되지 않는다. 목표는 촬영 확정부터 수정 가능한 카드까지 p50 3초, p95 5초 이하다. 충분한 비캐시 표본과 모바일 네트워크 측정 전에는 목표로만 표시한다.

## 실행·검증 원칙

- 각 단계는 작은 독립 변경으로 구현한다. 기본 경로를 유지한 채 후보 실험을 격리하고, 채택 결정 후에만 실제 경로를 전환한다.
- 단위 테스트는 자르기 좌표·필드 정규화·오류/빈 값·모델 응답 검증을 확인한다. 브라우저 E2E는 촬영 또는 파일 선택→수정→기존/신규 인물 선택→저장, 실패→재시도를 확인한다.
- 단계 완료 시 `npm run verify`, 기존 Phase 5 검증, 필요한 범위의 실제 제공자·DB 검증을 실행한다. 실제 API 호출은 합성 입력으로 제한해 먼저 경로를 검증하고, 실제 명함 비교 결과는 별도로 기록한다.
- 이번 범위에는 다중 명함 자동 분할, 명함 양면 연결, OCR 모델 자체 학습, 전체 관계 기억 아키텍처 교체를 포함하지 않는다.
