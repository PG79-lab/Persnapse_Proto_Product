# LC100 20분 개선·기울기/회전 탐색 설계

기준일: 2026-10-13. **상태: 사용자 OK 후 20분 탐색 구현·측정 수행.** 아래는 승인된 실행 설계이며 실제 완료 범위는 [결과 보고](../operations/card-quick-optimization-results-2026-10-13.md)를 따른다.

이 문서는 앞선 1~2 작업일·27장 전체 정답·54회 OCR 계획을 대체한다. 목적은 짧은 시간에 작은 개선을 적용하고, 다음 최적화 방향을 실험으로 파악하는 것이다.

## 1. 시간과 범위

**사용자 OK 이후 구현 시작부터 결과 보고까지 경과 시간 20분 이내**로 제한한다. 설치·서버 준비·테스트·외부 호출 대기 역시 이 시간에 포함한다. 환경 준비에 시간이 들면 평가 규모를 줄이고, 시간을 늘리지 않는다.

| 시간    | 작업                                            | 종료 시 남길 결과                        |
| ------- | ----------------------------------------------- | ---------------------------------------- |
| 0~2분   | Git/환경 확인, 대표 사진 선정, 기존 후처리 측정 | 입력 목록·baseline·원본 hash             |
| 2~6분   | 결과를 유지하는 후처리 반복 접근 개선           | 작은 코드 변경·동일 출력 비교            |
| 6~12분  | 보정 결과 90도 회전 지원, 기울기·회전 경로 확인 | OCR에 전달되는 실제 회전 JPEG            |
| 12~17분 | 소규모 전후 시간·테두리 평가, 준비되면 OCR 비교 | 사례별 수치·문제 목록                    |
| 17~20분 | 관련 검증·기존 HTML 활용·결과 보고              | 변경 위치·PASS/PARTIAL/NOT_RUN·다음 방향 |

위 시간은 배분안이다. 17분부터 새 기능을 추가하지 않는다. 시간 내 검증하지 못한 변경은 기본 동작에 반영하지 않거나 되돌린다. 진행 중인 측정은 중단하고 완료한 사례만 보고한다. 전체 고도화 완료로 표현하지 않는다.

## 2. 1단계: 작은 속도 개선

대상은 `card_recognition/detectors/docaligner.ts`의 픽셀 루프다. `resized.data32F`, `mask.data`를 루프 밖에서 한 번 가져와 재사용한다. threshold·Otsu·contour·centroid와 입력 해상도는 그대로 유지한다. Mat resize/delete 이후에 오래된 view를 사용하지 않는다.

- 같은 heatmap·이미지 크기에서 기존/개선 후처리를 각각 3회 측정한다. 가능한 경우 같은 이미지를 두 번 실행해 첫 실행과 이후 실행을 구분한다.
- 점 개수·유효성/실패 판정 일치, 준비 이미지 좌표 차이 최대 0.01px 이하를 확인한다.
- 후처리 중앙값·실측 범위, 측정 가능한 전체 감지/보정 시간을 보고한다. 소수 사례에서 p95/p99나 전체 27장의 정확도를 추정하지 않는다.
- 성능 향상률은 실측 결과로 보고하며 기존의 50%/30% 목표를 이번 합격 조건으로 쓰지 않는다. 기존 경합 포함 cold 수치를 새 결과의 baseline으로 사용하지 않는다.

**Worker·모델 재사용은 이번에 초기화 비용을 확인하고 다음 구현 방향으로 기록한다.** 공유 수명·작업 직렬화·취소/timeout 복구를 검증해야 하므로 20분 작업에 런타임 구조 변경을 함께 넣지 않는다. 제한 해상도 후처리·모델 교체·정밀화도 후속으로 미룬다.

## 3. 비스듬한 촬영·회전된 명함 처리

### 처리 방침

비스듬한 촬영은 기존 네 모서리 기반 원근 보정으로 평면화한다. 감지 실패·잘못된 네 점은 수동 모서리 편집으로 복구한다. `orderCardCorners`의 순환 시작점은 화면 위치 기준이므로 명함의 글자 방향을 보장하지 않는다.

따라서 **보정 이미지 확인 단계에서 90도 회전 버튼**을 제공한다. 반복 클릭으로 90/180/270도를 지원한다. 자동 글자 방향 판정은 이번 범위에서 구현하지 않는다.

- 회전은 CSS 미리보기만 바꾸는 것이 아니라 실제 JPEG 바이트를 생성한다. 90/270도에서는 width/height를 교환한다.
- 표시·다운로드·OCR 입력은 같은 최종 회전 파일을 사용한다. 현재 display 저장과 retry OCR 경로도 그 파일을 받도록 연결을 확인한다.
- 원본 파일과 원본 좌표계의 모서리는 유지한다. 회전 각도는 작업 상태에 보관하고, 반복 회전은 기준 보정본에서 생성해 연속 JPEG 재압축을 줄인다.
- 새 사진·모서리 재보정 시 이전 회전 결과를 폐기/초기화하고 revision으로 늦은 결과 반영을 막는다. 회전 처리 중 OCR을 비활성화한다.
- 회전이 실패하면 이전 유효 보정본을 유지하고 오류를 표시한다. 전면 저장 구조 변경은 하지 않는다.

### 확인 사례: 최대 10건

- 실제 27장 중 대표 4장: 정면 1, 비스듬한 촬영 2, 기존 자동 실패/수동 보정 대상 1. 실제 분포가 다르면 선정 사유를 기록한다.
- 대표 1장의 0/90/180/270도 입력 4건. 원본은 수정하지 않고 테스트 사본을 만든다.
- 정답 사각형을 아는 합성 원근 변형 2건. 이미지 밖으로 잘리지 않도록 생성하고 검증 좌표를 함께 변환한다.

해당 사례에서 감지 → 보정 → 방향 조정 → 올바른 OCR 입력 준비가 가능한지 확인한다. 감지가 실패하면 수동 복구 성공을 별도로 표시한다. 합성 변형 결과를 독립적인 실제 명함 정확도로 간주하지 않는다.

**임의의 심한 기울기·가려짐·모든 각도에서 자동 처리가 무조건 성공한다고 보장하지 않는다.** 이번 목표는 대표 사례에서 자동 처리 또는 수동 보정/회전으로 완료 가능한 경로를 확보하는 것이다. 실제 비율 복원은 기존 estimated 정책을 유지한다.

## 4. 2단계: 소규모 품질 탐색

### 테두리

실제 대표 사진 중 최대 3장에 감지 결과를 숨긴 상태로 네 모서리를 지정하고 확대 확인한다. 시간 내 판독 가능한 사진만 평가하고 미지정/애매한 사례를 별도 기록한다. 단일 작성자의 잠정 정답이며 독립 검수된 GT가 아니다.

기존 `boundaryMetrics`와 HTML 도구를 재사용한다. EXIF 정규화된 준비 이미지의 픽셀 좌표에서 polygon IoU·평균/최대 모서리 오차를 계산한다. 저장 좌표는 [0,1]이고 평가 전에 x×width/y×height로 환산한다. 모서리 오차 분모는 정답의 긴 대각선이다.

- 사례별 참고 통과 기준: IoU ≥0.985 및 최대 모서리 오차 ≤1.5%.
- 자동 실패는 실패에 포함하고 수동 보정 결과와 구분한다. 미평가 사진은 분모에 넣지 않는다.
- 보정 내용 잘림·거꾸로/옆으로 된 글자·심한 왜곡은 육안 판정과 사유를 기록한다.
- 27장 전체 정답 작성·3회 반복 벤치마크·정식 품질 gate는 후속이다. 기존 27장 비교 HTML은 보존한다.

### OCR: 시간 안에 준비된 경우만

서버·자격증명·비용 정책이 이미 동작하는 경우 대표 1~2장에만 보정 전/후 비교한다. **최대 4회 유료 호출 시도**, 자동 재시도 없음. 제공자·모델·prompt/schema를 고정하고 기존 서버 서비스와 quota를 이용한다. 호출 제한을 우회하지 않는다.

보정 후 입력은 사용자가 확인할 최종 방향의 JPEG이며, 보정 전 입력은 기존 앱 원본 전처리 정책을 거친 이미지다. 이름·회사·전화·이메일 중 읽을 수 있는 필드를 먼저 전사해 정확 일치 수와 개선/동일/악화를 확인한다. 입력 hash·크기·실제 호출/캐시 hit도 기록한다.

자유 배치 전체 문자 CER, 27장 전체 OCR 평가, 새 OCR 도구·provider 도입은 제외한다. 환경 준비나 외부 응답 대기가 길면 OCR은 NOT_RUN/일부 완료로 보고한다. Mock 확인은 실제 OCR 정확도 평가로 표시하지 않는다. 이미지·정답·OCR 출력은 Git 제외 로컬 output에 저장하고 최종 명함/Identity 저장은 수행하지 않는다.

## 5. 검증·보고·후속

이번 변경은 소규모 실험이다. 관련 geometry/후처리/회전 테스트, typecheck와 해당 UI/Mock OCR 전달 확인을 우선 수행한다. 시간이 남으면 lint·전체 unit·빌드를 실행한다. 20분 시간 제한으로 미완료한 검증은 NOT_RUN으로 명시하고, 큰 단계의 전체 검증이 완료된 상태나 배포 가능한 상태로 표시하지 않는다. 커밋·배포는 이번 요청에 포함하지 않는다.

산출물은 변경 코드, 사례별 JSON/CSV, 기존 HTML을 활용한 테두리·보정·방향 비교, 짧은 결과 보고서다. 새 범용 dashboard는 만들지 않는다. 로컬 자료는 `output/card-rectification/optimization-quality-2026-10-13/` 아래 보관하고 원본 27장 hash와 기존 미커밋 변경을 보존한다.

최종 보고는 다음만 정리한다.

1. 변경한 기능과 전후 후처리 시간, 측정 장수.
2. 기울기·0/90/180/270도 사례의 자동/수동 처리 여부, 회전 JPEG의 OCR 전달 여부.
3. 잠정 정답의 IoU·오차, 실제 OCR 비교 결과 또는 미실행 사유.
4. PASS/PARTIAL/FAIL/NOT_RUN, 실제 경과 시간, 다음에 할 최적화 2~3개.

후속 최적화는 측정에 따라 Worker/모델 재사용 → 더 넓은 GT/OCR 평가 → 후처리 해상도 개선 순서를 검토한다. 이후 사용자 확정 방향인 원본 보존 → 이미지 처리 → **명함 디지털 재현**으로 진행한다.
