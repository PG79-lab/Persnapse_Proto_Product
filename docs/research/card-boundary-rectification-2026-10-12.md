# 명함 외곽 감지·2D 평면 복원 개선 조사

- 조사일: 2026-10-12
- 상태: 조사·개선 설계 완료. 모델 추론·실촬영 성능 비교·제품 적용은 아직 수행하지 않음.
- 확정 범위: 단일 명함의 외곽·네 모서리 감지와 원본 이미지 기반 2D 평면 복원.
- 적용 화면: 통합 워크스페이스 `/#cards`. 작업 모듈: `card_recognition/`.
- 사용자의 우선순위: 정확성·원본 시각 보존 우선, 가능한 범위에서 빠르게 처리.

## 1. 현재 구현에서 확인한 문제

실패한 실촬영 이미지가 제공되지 않았으므로 아래는 코드에서 확인한 구조적 한계다. 실제 실패 원인별 비율을 측정한 결과는 아니다.

| 항목          | 현재 코드                                                                                           | 발생 가능한 문제                                                                           |
| ------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 명함 식별     | `restore-image.ts`의 고정 Canny(45, 140) → 4점 윤곽 → 가장 큰 면적 선택                             | 책상·화면·배경 사각형을 명함으로 선택. 어두운 명함, 흰 배경 위 흰 명함, 반사·그림자에 취약 |
| 후보 생성     | 단일 회색조 경로, `approxPolyDP` 허용 오차 2.5%                                                     | 부분적으로 끊긴 테두리나 둥근 모서리에서 유효 후보 누락                                    |
| 크기 제한     | 사진의 12% 미만·98.5% 초과 영역 제외                                                                | 작은 명함과 사진을 거의 채운 명함/스캔본을 놓침                                            |
| 모서리 정밀도 | 검출용 긴 변 최대 1280px, 원본 경계에서 재조정 없음                                                 | 오차를 큰 이미지에 확대 적용하여 인쇄 내용 잘림·배경 유입                                  |
| 출력 비율     | `geometry.ts`: 사진 속 마주 보는 변 길이 중 큰 값으로 가로·세로 결정                                | 원근으로 짧아진 변을 실제 명함 길이로 취급하여 가로·세로 비율 왜곡                         |
| 해상도        | `drawSource`: 전체 사진 긴 변 2560px로 축소 후 warp                                                 | 사진 안에서 명함이 작으면 명함 자체의 유효 해상도가 크게 낮아짐                            |
| 재개 품질     | 최초 복원은 메모리의 입력 파일, 새로고침 후 수동 복원은 최대 2560px·JPEG 재인코딩된 저장 `original` | 같은 촬영본에서도 첫 처리와 재개 처리의 픽셀 품질이 다를 수 있음                           |
| 실패 판단     | 모델/코너 신뢰도, 배경과 명함 구분 점수, 내용 잘림 검증 없음                                        | 틀린 사각형도 복원 미리보기로 제시됨                                                       |
| 실행·수정     | 메인 스레드 OpenCV, 수동 점은 고정 8%/92%에서 시작                                                  | 큰 처리 중 UI 지연 가능. 수동 수정 시 기존 검출 후보를 활용하지 못함                       |

### 비율 계산의 작은 재현 검사

실제 `rectifiedCardSize`를 그대로 호출했다. 가로:세로 1.8인 직사각형을 기준으로, 정면 좌표와 가로가 원근으로 짧아진 사각형 좌표를 비교한 기하 검사다. 이미지 인식 벤치마크가 아니다.

| 입력 좌표 사례                                          | 현재 출력 크기 | 현재 출력 비율 | 알려진 합성 원본 비율 대비 오차 |
| ------------------------------------------------------- | -------------- | -------------- | ------------------------------- |
| 정면 `(100,100),(1000,100),(1000,600),(100,600)`        | 900×500        | 1.8            | 0%                              |
| 투영된 사각형 `(100,100),(400,130),(380,370),(110,380)` | 301×280        | 1.075          | 약 40.3%                        |

네 점이 정확해도 출력 비율 정책이 틀리면 평면 복원은 찌그러질 수 있다. 일반적으로 사진의 네 모서리 좌표만으로 실제 물리적 비율이 확정되는 것은 아니다. 실제 크기·카메라 보정값·추가 가정이 필요한 부분이며, 현재는 사진 속 변 길이를 이용한 근사에 해당한다.

DocAligner 공식 SmartDoc 평가의 Jaccard Index는 LC100 0.9892, FastViT-T8 0.9906이다. 문서 데이터·평가 방법에 한정된 제작자 보고 수치이며, 우리 명함에서의 성공률·정확도·지연이 아니다. LC050 heatmap은 문서에 나오지만 현재 레포의 heatmap 설정에는 LC100/T8/SA24만 확인되어 즉시 재사용 후보에서 제외했다.

### 가중치·입출력 조사에서 확인한 사항

- DocAligner ONNX의 공개 다운로드를 확인했지만 다운로드·추론·해시 계산은 하지 않았다. 실제 후보 검증에서 파일과 SHA-256을 고정한다.
- DocAligner 참고 경로는 BGR 이미지 → 직접 256×256 resize → NCHW float32 0..1 → `img` 입력, `heatmap` 출력이다. 기본 center crop은 꺼져 있다. 임의로 RGB/letterbox/center crop으로 바꾸지 않고 제공자의 기준 전처리를 먼저 재현한다.
- DocQuadNet의 기준 전처리는 RGB, 검정 letterbox 256×256, NCHW float32 0..1이다. `corner_heatmaps`와 `mask_logits`가 나오며 출력 후 좌표를 원본으로 역변환한다. 모델마다 전처리 어댑터가 필요하다.
- DocQuadNet 제작자가 공개한 ONNX 해시: `a0411380e01174da18c004afc2ffc4f71bcd01dbecef531b2b6337acfdd3ac85`. 현재 배포 ORT와 동일 버전이라고 가정하지 않는다.
- 웹에서는 ONNX Runtime Web으로 WASM을 기본 비교하고 WebGPU를 별도로 측정한다. GPU 경로의 연산 지원·초기화·실행은 실제 모델과 기기에서 확인한다. 다른 프로젝트의 Android/서버 속도를 모바일 웹 속도로 가져오지 않는다.

## 3. 권장 해결 방법

**학습 모델로 대략적인 명함 위치와 모서리를 찾고, 원본 해상도에서 경계를 정밀하게 맞춘 뒤, 검증된 사각형과 출력 비율로 한 번만 원근 보정한다.**

| 단계               | 방법                                                                                                          | 핵심 제한                                                                       |
| ------------------ | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 1. 입력 정리       | EXIF 방향을 한 번 적용. 저해상도 검출 입력과 고해상도 복원 소스를 분리                                        | 작은 모델 입력을 복원 이미지로 사용하지 않음                                    |
| 2. 모서리 후보     | LC100/T8/DocQuadNet을 같은 데이터로 비교. 기존 OpenCV도 대조군으로 유지                                       | 한 모델을 사전 최종 선정하지 않음. 가장 큰 사각형만으로 선택하지 않음           |
| 3. 고해상도 정밀화 | 예측된 네 변 주변 좁은 띠에서 RGB/명암 경계·직선 fitting·교점으로 좌표 조정                                   | 더 선명한 인쇄선/그림자로 끌려가면 조정을 버림. 둥근 코너는 변의 교점 기준 검증 |
| 4. 후보 검증       | 네 점의 볼록성·중복·자기 교차·사진 경계·heatmap 명확성·변 경계 지지 검사. mask 모델은 영역과 모서리 일치 검사 | 사다리꼴이 정상인 원근 사진에서 사진 속 각도가 90도가 아니라고 거부하지 않음    |
| 5. 비율 결정       | 알려진 명함 실측 비율 또는 충분한 카메라/기하 정보가 있으면 사용. 불확실한 경우 미리보기에서 간단한 비율 확인 | 모든 명함에 90×50 등 한 규격을 강제하지 않음. 자동 추정의 신뢰도를 별도 관리    |
| 6. 평면 복원       | 기존 OpenCV `getPerspectiveTransform`/`warpPerspective` 재사용. 높은 해상도 소스에서 한 번만 resampling       | 숨겨진 모서리·반사로 사라진 글자·없는 픽셀을 생성해 채우지 않음                 |
| 7. 표시·저장       | 원본과 보정 후보를 비교. 낮은 신뢰도면 검출한 점부터 수동 수정. 완전한 스캔본은 별도 `already-flat` 후보 처리 | 기존 사용자 OK 이후 결과 표시·승인 후 저장 경계를 유지                          |

### 출력 화질

- 전체 사진을 먼저 2560px로 줄이는 대신, 검출된 명함의 실제 픽셀 영역을 기준으로 복원 해상도를 정한다.
- 원본 해상도의 국소 영역을 사용하고 출력 픽셀 수·메모리 상한을 함께 관리한다. 사진 전체 RGBA 6000×4000은 한 버퍼만 약 96MB이므로 무조건 고해상도 전체 Mat을 여러 개 만드는 방식은 피한다.
- 원근 보정 이후 JPEG 인코딩은 마지막에 한 번 수행한다. 저장된 `original`이 축소·압축본이라는 기존 한계와 재개 시 사용할 소스 전략을 함께 검토한다.
- 색과 종이 질감을 보존하는 경로를 기본으로 한다. 이진화·강한 CLAHE·자동 샤프닝은 기본값으로 켜지 않고 별도 비교한다. 보간법은 bilinear/cubic/Lanczos 계열을 글자·색·지연 기준으로 비교한다.
- 생성형 업스케일이나 디자인 재생성은 이번 개선의 필수 요소가 아니다. 먼저 외곽·비율·원본 픽셀 사용의 손실을 해결한다.

### 성능과 실행 위치

- 1차 후보는 `onnxruntime-web` + Web Worker + 기존 OpenCV. WASM/WebGPU는 동일 모델·입력으로 측정한다.
- WASM은 단일 스레드+Worker부터 비교한다. 멀티스레드는 브라우저 지원과 `crossOriginIsolated`가 필요하다. WebGPU는 WASM proxy Worker 설정을 그대로 사용하지 않고 전용 Worker에서 실행을 검증한다. 런타임 JS와 WASM 자산 버전을 일치시킨다.
- 모델·런타임은 명함 화면/카메라 진입에서 준비하고 세션을 재사용하는 안을 검증한다. 복원 계산을 OCR 검토 중 병행할 수 있지만 결과 표시·저장은 기존 OK 계약을 따른다.
- 품질 기준 통과 후에만 FP16/INT8을 비교한다. 모델 추론 시간만 아니라 다운로드, decode, 정밀화, warp, encode, 메모리와 UI 정지를 측정한다.
- 브라우저 실패/부족한 성능이 확인되면 ONNX CPU 추론 서비스나 고성능 서버를 후보로 둔다. 처음부터 Python 서비스를 Vercel Next 함수에 넣는 것으로 가정하지 않는다.

네 모서리는 동일한 정의로 라벨링하고, 여러 사진이 같은 물리적 명함이면 같은 분할에 넣는다. 실제 20장은 파일럿이며 예를 들어 10장 튜닝·10장 보류 검증으로 분리한다. 소량 표본의 p95와 실패율을 일반 사용자 전체의 성능으로 확정하지 않는다.

### 기준과 실험 분리

| 지표        | 정의·방법                                                            | 1차 제안 목표(미확정·미달성)                                           |

| 외곽 일치   | 예측 사각형과 정답 사각형의 polygon IoU, 실패 포함                   | ≥0.98을 출발 기준으로 검토                                             |
| 내용 보존   | 필수 인쇄 내용·로고가 잘리는지 수동 확인                             | 검증 표본에서 잘림 0건                                                 |
| 비율 오차   | 실제 비율이 알려진 명함에서 출력 비율과 비교                         | 상대 오차 ≤2%                                                          |
| 복원 수용률 | 사람이 원본과 보정 후보를 보고 수정 없이 채택하는 비율               | 파일럿 ≥90% 검토                                                       |
| 시각적 보존 | 정면 스캔/합성 정답과 정렬 후 글자·색·질감 비교                      | 불필요한 손상·가짜 픽셀 없음. 사진과 복원본의 raw SSIM만 비교하지 않음 |
| 속도·리소스 | Android Chrome/iPhone Safari, 최초·반복, p50/p95·최대 메모리·UI 정지 | 정확성 통과 후 최대한 단축. 모델 비교 전에 기기별 기준 설정            |

1. **검출기 비교:** 출력 비율·warp·encode를 고정하고 OpenCV/LC100/T8/DocQuadNet의 코너만 바꾼다.
2. **복원기 비교:** 사람이 지정한 정답 코너를 고정하고 출력 비율·보간·소스 해상도만 바꾼다.
3. **정밀화 효과:** 동일 모델에서 경계 정밀화 적용 전·후의 코너 오차와 잘림을 비교한다.
4. **최종 흐름:** 통합 `/#cards`에서 촬영/파일 입력 → 검출 → 필드 OK → 복원 확인 → 저장·재개를 검증한다.

### 판정 기준과 결론

사용자가 제공한 별도 조사안의 PP-StructureV2, YOLOv8/v10 Nano+OCR, ONNX Runtime Web+OpenCV 구성을 공식 문서·저장소와 대조했다. 현재 확정 과제는 명함 외곽·네 모서리 감지와 원본 픽셀 기반 평면 복원이고, 정확성·원본 보존이 우선이다.

**현재 과제의 기능 적합성에서는 기존 문서 모서리 모델이 더 직접적인 후보다.** PP-StructureV2 내부 레이아웃 분석과 일반 YOLO Detect를 바로 대체제로 넣는 근거는 부족하다. ONNX Runtime Web+OpenCV는 기존 제안과 같은 실행 방향이다. 이는 실제 사진에서 기존 모델이 더 정확하거나 빠르다는 실측 판정은 아니다.

### 첨부안의 주요 주장 검증

1. **Paddle의 파이프라인 통합성은 사실이다.** V2는 방향 보정, 내부 레이아웃 분석, OCR, 표 구조, KIE, Word/PDF 레이아웃 재구성을 연결하고 모듈별 사용도 지원한다. 이때 Word/PDF 재구성은 촬영 명함을 원본과 같은 픽셀 이미지로 평면 복원하는 작업과 구분된다. 기본 layout의 문서 클래스가 이름·회사·휴대폰 같은 명함 필드 종류를 바로 의미하지도 않는다.
2. **전체 V2의 모바일 브라우저 실행 보장은 확인되지 않았다.** 공식 Paddle.js 예시는 PP-OCRv3 문자 검출·인식이고, 현재 PaddleOCR.js 브라우저 문서도 PP-OCR 검출·인식 SDK를 설명한다. 이러한 OCR 웹 지원을 PP-StructureV2의 모든 모듈 지원으로 확대 해석하지 않는다. Paddle-Lite 네이티브 이식과 일반 모바일 웹 실행도 별도 경로다.
3. **YOLO 기본 사각형은 원근 명함의 네 모서리가 아니다.** 일반 Detect는 축 정렬 박스이고 OBB는 중심·가로·세로·회전으로 표현한 회전 직사각형이다. OBB의 4점 출력도 일반 원근 사다리꼴을 표현하는 자유로운 4개 코너 출력과 같지 않다. 정확한 명함 네 점을 얻으려면 전용 keypoint 학습 또는 segmentation+코너 fitting이 필요하다. V10 기본 공식 모델은 Detect이다.
4. **YOLO의 수 ms 주장은 조건부다.** 공식 YOLOv8n 표는 640 입력에서 CPU ONNX 80.4ms, A100 TensorRT 0.99ms를 보고한다. 특정 GPU 추론 값을 모바일 웹·업로드·후처리·OCR·전체 지연으로 일반화할 수 없다.
5. **구역별 OCR의 우위는 명함에서 별도 평가해야 한다.** 내부 layout 단계를 추가하면 비용도 생긴다. 잘못된 crop은 `Tel/Fax/HP` 표기와 숫자, 회사·이름 관계를 분리할 수 있다. 큰 문서의 특정 영역만 읽을 때와 작은 명함 전체를 읽을 때의 이익은 다를 수 있다는 제품 관점의 추론이다.
6. **전처리로 정확도가 2배 이상 오른다는 일반 기준은 확인하지 못했다.** 첨부 내용에는 평가 데이터·지표·전후 결과가 없다. 올바른 보정은 도움이 될 수 있지만 잘못된 crop·비율·해상도 손실은 악화 요인이다. V2 논문의 경량 layout 모델 속도 개선 보고를 원근 보정의 정확도 배수로 바꾸어 해석하지 않는다.
7. **모바일 브라우저라는 이유만으로 한국어 OCR 정확도가 낮아진다고 단정할 수 없다.** Tesseract.js는 Tesseract를 WASM으로 실행하는 래퍼이며 모델 정확도를 개선하는 별도 OCR 모델이 아니다. 언어 가중치·입력 해상도·폰트·전처리·메모리 조건을 구분해 측정해야 한다.

### 비교 후 권장사항

- 기존 코너 모델+고해상도 경계 정밀화+비율 정책을 우선 비교하는 방향을 유지한다. DocCornerNet을 포함한 각 후보의 실제 명함 성능은 모두 미검증이다.
- Paddle을 복원 후보로 평가할 때는 UVDoc/문서 전처리 모듈을 구체적으로 지정한다. 현재 PP-StructureV3에는 `use_doc_unwarping`을 통해 별도 보정 모듈을 켜는 경로가 있다. V2 전체 파이프라인 도입을 복원 해결책으로 가정하지 않는다.
- UVDoc의 공식 Paddle 배포 크기는 30.3MB이다. 공개 DocUNet 결과와 서버 시간은 명함·모바일 웹 결과가 아니므로 우리 입력에서 품질과 전체 지연을 비교한다.
- YOLO는 명함용 segmentation/4-keypoint 가중치가 있을 때 평가하거나 다중 명함 단계에서 학습을 검토한다. Ultralytics는 AGPL-3.0/Enterprise 라이선스를 명시하므로 실제 선택한 구현·가중치의 조건을 확인한다. 상용 사용 자체가 금지된다고 해석하지 않는다.
- 첨부한 3단계는 OpenCV 외곽 검출과 원근 보정이 먼저 성공한다는 전제다. 그 첫 단계가 현재 개선 대상이므로 후단의 내부 layout/OCR 추가만으로 초기 crop과 비율 문제를 해결한다고 판단하지 않는다.

제품 코드는 변경하지 않았으며 실제 모델 간 벤치마크도 수행하지 않았다. 이 비교는 기능 계약·공개 가중치·실행 지원·현재 제품 맥락에 대한 조사 판단이다.
